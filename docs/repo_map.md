## 3. API surface (all in `ikigai_masala-main/api/app.py`)

| Method | Route | Purpose |
|---|---|---|
| GET  | `/api/v1/clients` | list clients (`clients` = names; `clients_detail` = `[{name, city, is_launch_site}]` for the sidebar city + launch-site filters) |
| POST | `/api/v1/plan` | generate full menu (a 500 from an INFEASIBLE solve now carries the pre-flight `rule_diagnostics` + `summary` — it cleared the blocking gate, so its *warnings* are the only clue to which rules conflict; `ui.api_client.SolverFailedError` (a `RuntimeError` subclass, same shape as `RuleDiagnosticsBlockedError`) surfaces them) (optional `counter_index` picks which counter to solve; optional `alternates` 0..`MAX_ALTERNATES`=4 → ranked near-optimal distinct menus in an `alternates` list, primary stays in `solution`; response carries `counter_mode`/`counter_count`/`counter_index`/`counter_name`; each item carries `is_nonveg` and **`is_pinned`** — true for a cell the solve did not choose, i.e. a global staple or a `constant_items` pin. Recorded by `MenuSolver._rows_to_week_plan`, the code that does the pinning, and read back by `ui.formatters.pinned_slots_from_solution`. `/saved-plan` deliberately does NOT set it: a replayed plan was not solved, so which cells were pinned AT THE TIME is unknowable and today's config would mark cells a later edit has unpinned) (optional **`shared_items`** = `[[iso_date, slot_id, item], …]` → cross-counter common-category sync: `_merge_shared_items` folds them into `forced_items` (same narrow-the-cell mechanism as a client constant), an explicit constant pin wins; the planner passes the primary counter's shared-slot dishes so later counters serve the same dish per day — see note 22) (response also carries **`relaxations`** when the solve under-enforced a rule — absent on a clean plan, so a clean body is unchanged — collected by `RelaxationCapture` around the solve and fed to `/explain`, note 31) |
| POST | `/api/v1/regenerate` | regenerate selected cells (optional `counter_index`; items carry `is_nonveg` and `is_pinned`; optional **`exclude_items`** = `[[iso_date, {slot_id: [item_base, …]}], …]` → the dishes already shown for each cell this session, folded into the regenerator's `extra_forbidden` so repeated clicks stop cycling A→B→A) |
| POST | `/api/v1/save` | persist plan → history (single `week_plan`, or multi `counters: [{name, week_plan}]` → nested `menu_history`). **Dish names are canonicalised to the ontology's spelling first** (`_canonicalise_saved_plan`, note 28) — history is read back by the cooldown/freshness/cadence rules, which compare the stored string against `pool['item']`, so a display name stored as `dal tadka` would silently never match `dal_tadka`. What cannot be resolved is stored as given and reported in `unknown_items` + `warning` (both absent on a clean save); **never rejected** — an off-ontology `constant_items` pin is legitimate and a generated plan must not be lost to an unrecognised name |
| POST/GET | *(services in a day)* | `/plan` and `/save` take **`meal`** (`lunch` default; `breakfast`/`lunch`/`snacks`/`dinner`), `/saved-plan` takes it as a query arg, and `menu_history`'s primary key is `(client_name, service_date, meal)` — an unsaved dinner is not a missing row the next plan notices, it is a menu the cooldown and the freshness objective never heard of. `/plan` also takes **`exclude_items`** = `{iso_date: [item, …]}`, folded into `banned_by_date` by `_merge_excluded_items`: the two services are SEPARATE SOLVES, so `unique_items` cannot see across them and the cooldown only reads SAVED history, which is after the duplicate is on screen. **`meals`** is a `clients.meals` JSONB LIST on `GET/PUT /client-config` and `POST /client` — `breakfast`/`lunch`/`snacks`/`dinner`, defaulting to lunch+dinner for every client. It replaced a `serve_dinner` boolean, which could only ever say "lunch, and maybe dinner". See note 39 |
| GET  | `/api/v1/editor-metadata` | slot/theme/**city** metadata for editor (`available_cities`, `default_off_slots`, `default_item_cooldown_days`, `available_client_pools`, `client_pools_by_city`). Optional `?city=` scopes `available_client_pools` to that city's item list; without it the list is the cross-city union. The editor does **not** use that union — `customisation.main.pools_for_city` reads `client_pools_by_city` and returns `[]` for a city with no pools, because offering a Bangalore token to a Pune client is worse than offering none (the PUT rejects it, and it would match nothing in Pune's list anyway) |
| GET  | `/api/v1/regions` | regions a city's item list can theme a day with (`?city=`), each with its per-slot depth, plus `theme_compatibility` and an `available` flag. **False for every city today** — the `state_origin`/`admin_type` columns arrived with the client's corrected workbooks and those are not installed, so the planner hides the control. Its own endpoint rather than a field on `/editor-metadata` (which already costs every city's workbook): the planner calls it only when the regional toggle is switched ON, so a user who never asks for a regional day pays nothing. See note 40 |
| POST | `/api/v1/pool-preview` | F5: eligible distinct item count + category-wise counts for a set of `source_pools` (common always included). Optional `city` selects which city's item list is counted |
| GET  | `/api/v1/client-config/<name>` | fetch client config (incl. `city`, `serve_weekends`, `item_cooldown_days`, `source_pools`, `is_launch_site`, **`shared_categories`** — base slots synced across counters: the DB `clients.shared_categories` value when set, else the file value from `MenuRuleLoader.get_shared_categories`) |
| PUT  | `/api/v1/client-config/<name>` | update client config (accepts `city`, `serve_weekends`, `item_cooldown_days`, `source_pools`, `shared_categories`) |
| POST | `/api/v1/client` | create client (accepts `city`, `serve_weekends`, `item_cooldown_days`, `source_pools`, `shared_categories`) |
| DELETE | `/api/v1/client/<name>` | delete client |
| POST | `/api/v1/diagnose` | dry-run pre-flight: run every rule's `diagnose()` + built-in pool/colour diagnostics; returns structured `rule_diagnostics` + `summary` + `counter_index`/`counter_name`/`counter_count` (the same pass `/plan` runs as its 422 gate). **Honours `counter_index`** — it used to build its inputs from the primary counter regardless, so every multi-counter client got a clean bill of health for counter 0 while the counter being planned was unsatisfiable |
| POST | `/api/v1/explain` | explain a plan the caller already has: `{client_name, start_date, num_days, counter_index?, solution, relaxations?, chef_read?, region_days?}` → `{days: [{date, weekday, theme, **overview**, **overview_source**, bullets, prose, checks, **pairings**, provenance, plate_profile, relaxations, **chef_read**, llm_used, reason}]}`. **`chef_read: true` is the only thing that calls a model for judgement** — the planner's "Ask the chef" button, separate from "Explain this menu", because the read costs up to 3 calls per DAY and a plain explanation must never pay for it; `EXPLAIN_CHEF_READ_ENABLED` is a kill switch, not the trigger. **`region_days` is an INPUT for the same reason `relaxations` is**: a Tamil Nadu Tuesday and a themeless Tuesday can hold the same dishes, so the region is not recoverable from `solution` and the read describes a regional day as an ordinary one without it — nothing errors, the explanation just stops mentioning the thread the day was built around. Sent when the planner's regional toggle is on, the same gate `/plan` uses. **`chef_read`** in the response is the model's JUDGEMENT of the day (`api/explain_llm.py::explain_chef_read`), the opposite bet from `overview` above: `{source, reason, client_read, internal_read, star, weak_spots, data_doubts, attempts}`, `None` when nobody asked, and `source=None` with a reason when it is switched off (`disabled`), keyless (`no model key`), throttled (`rate limited`) or rejected by the checks three times. **A transport failure spends an ATTEMPT, not the day** — the rule used to be "a network failure is not retried, retrying only spends quota", and on a real 7-day plan that cost one day's read to a single cold-start read timeout while two unused attempts stood by. 429 and a missing key stay terminal because a second attempt gets the same answer; `_post_model` fills an `outcome` dict with the failure kind so the day can tell them apart. Only `client_read` may leave the building; `internal_read` and `data_doubts` are for the kitchen, which is why `ui/formatters.py::chef_read_sections` splits it into "For guests" and "For the kitchen" and returns NOTHING unless the read passed every check — half a read is worse than none. `chef_read_status` says why a day has no read, but only once asked. See `docs/chef_read_architecture.md`. Never solves — its own endpoint rather than part of `/plan` so a caller who does not want the explanation does not pay for it and a failure here cannot cost anyone a menu. `bullets` are always present (`src/explain/renderer.py`); `prose` is null unless the optional model is on AND its reply passed `api/explain_llm.py::validate`. **`overview` is the primary surface** — the four-or-five-sentence paragraph a chef reads — and carries the MODEL's wording when one is configured and its reply validates, the deterministic `renderer.day_overview` otherwise; `overview_source` (`model`/`rendered`) says which, so a deployment can tell "the model is off" from "the model keeps being rejected" without reading logs. Swapping who writes the sentence changes nothing about what may be SAID: every claim still comes from the pack, and an unsourced number, an invented dish or a reply silent about a gap is still rejected whole. **`relaxations` are an INPUT** because only `/plan` can produce them (note 31) |
| GET  | `/api/v1/saved-plan` | fetch a previously saved plan from history |
| GET  | `/api/v1/metrics` | Prometheus-style metrics scrape |
| GET  | `/api/v1/health` | health check |

Helpers:
- `api/concurrency.py` — `@solver_gate` queue; caps active solves (dynamic CP-SAT workers).
- `api/config.py` — path constants, day/time limits, **per-city ontology resolution** (`city_excel_path`, `city_required_slots`, `CITY_ITEMS_DIR`, `DEFAULT_ONTOLOGY_CITY`).
- `api/rate_limit.py` — per-IP token-bucket throttle on `/plan` + `/regenerate`.

Hardening (all opt-in / non-breaking):
- `MAX_CONTENT_LENGTH_BYTES` (default 2 MB) caps request bodies; an over-limit
  body is rejected in `before_request` so the status is 413 rather than a 500
  swallowed by an endpoint's broad `except Exception`.
- `API_WRITE_TOKEN` (env, unset by default) gates the mutating endpoints via
  `@require_write_token` — `X-API-Key` or `Authorization: Bearer`. Unset means
  the API behaves exactly as before (open), so this changes nothing until an
  operator opts in. Reads are never gated.
- Rate-limit buckets: `plan` **`MAX_COUNTERS * 3`/min (18)**, `regenerate` 20/min, `write` 30/min
  (save / create / delete / config PUT), `diagnose` 20/min (also `/pool-preview`
  and `/explain`).

Beyond the optional write token there is no per-user authentication: reads are
public and the deployment relies on the network perimeter.

## 4. `src/` module map

### 4.1 `src/solver/` — CP-SAT solver
| File | Key symbols | Role |
|---|---|---|
| `menu_solver.py` | `MenuSolver.solve`, `SolverConfig`, `_Cell`, `_freshness_bonus` | cell-based CP-SAT: one bool var per (day, slot, candidate). Optional `recency_by_item` ({item_base: days-since-last-served}) drives the soft **freshness** objective (`_freshness_bonus`, note 24) — prefer dishes served long ago / never, `min(days, FRESHNESS_CAP_DAYS=30) * FRESHNESS_UNIT=3000` per candidate, bounded below one LOW soft-rule unit so any rule outranks it; never bans, never INFEASIBLE |
| `solver_context.py` | `SolverContext` | runtime bundle passed to rules |
| `solution_formatter.py` | `SolutionFormatter.to_dict` | solver output → API JSON (tags each item `is_nonveg` from a passed nonveg name-set, and `is_pinned` from a passed `{(date, slot_id)}` set) |
| `regenerator.py` | `MenuRegenerator.regenerate`, `similarity_score` | locks fixed cells, re-solves selected ones. `regenerate(..., extra_forbidden={(date, slot_id): {item_base, …}})` also blocks every dish already shown for a cell this session, so repeated clicks cycle through fresh dishes instead of flipping A→B→A (soft: falls back to the penalty path if blocking empties a cell). Passes `recency_by_item` through so replacements prefer fresher dishes too |
| `_helpers.py` | `weekday_type_for_config`, `strip_color_suffix`, `items_from_day`, `cell_is_skipped` | shared utilities. `cell_is_skipped(skip_cells, date, slot_id)` is the single skip predicate for `MenuSolver._build_cells` + `MenuRegenerator`: `skip_cells` holds `(date, base_slot)` entries (skip every expansion — what `slot_day_restriction` emits) **and** `(date, slot_id)` entries (skip one expansion — how a client constant pins `nonveg_main__2` while `__1` stays solved) |

### 4.2 `src/menu_rules/` — constraint system
Two-phase: `pre_filter_pool()` (cheap removals before CP-SAT vars), `apply()` (hard/soft constraints on model), `get_objective_terms()` (penalties/bonuses).

| File | Kind | Role |
|---|---|---|
| `base_menu_rule.py` | abstract | parent class |
| `menu_rule_loader.py` | loader | deserialize a rules JSON; `load_for_city(city)` resolves `data/configs/city_rules/<city>.json` + its `extends` chain (override by rule `name`, `disable` list), falling back to `DEFAULT_CITY`; `load_for_client()` merges per-client `{disable, rules, constant_items}` over the city list by name (legacy list form still works) |
| `cuisine_menu_rule.py` | hard | min cuisine variety |
| `color_rules.py` | hard + params | `ColorPairingMenuRule` (two named slots may not share a colour on a day) · `WelcomeDrinkColorMenuRule` (no repeat welcome-drink colour on adjacent days; optional **`slot_indices`** scopes it to named drink cells, which is what makes it compatible with a drink STAPLE — PhonePe is the only counter in the fleet running two drinks, a rotating detox water and a buttermilk every day, and a buttermilk is white on all five days, so across both cells the rule is INFEASIBLE the moment the staple resolves to a real dish rather than stamping as text. Measured. `day_welcome_color_vars` is keyed `(day, colour, slot_id)` for it; single-drink counters are unaffected) · **`ColorVarietyMenuRule`** — adds no constraints; it carries the *per-city numbers* for the built-in colour block (`min_distinct_per_day`(`_chinese`/`_biryani`), `max_same_color_per_day`, `max_same_color_reach`, `max_colors_at_reach`, `ignore_rice_gravy_color_diff_on_chinese_day`), read by `api._build_solver_config` via `solver_overrides()` against the `_RULE_OVERRIDABLE_CFG_FIELDS` allow-list. Bangalore wants 4 distinct with one colour allowed to reach 3 (the SolverConfig defaults, so it ships no such rule); Pune's rulebook R1/R2 want 3 distinct and a flat cap of 2, which is why the numbers had to leave `SolverConfig` |
| `unique_items_menu_rule.py` | hard | no repeats within horizon |
| `coupling_menu_rule.py` | hard | deep-fried rice/bread/veg-dry family (rulebook 34-42): liquid rice ⇒ deep-fried veg_dry/starter (scoped to active slots); deep-fried veg_dry ⇒ rice-bread + liquid rice; rice-bread ⇒ liquid rice; dosa bread + active nonveg ⇒ SI chicken gravy (availability-guarded); rice-bread & deep-fried veg_dry each ≤1 day/wk. All conditional upper bounds (never mandates, never INFEASIBLE). The old rice-bread⇔deep-fried-starter link is retired (rulebook §5) |
| `curd_side_menu_rule.py` | hard | fill curd/raita slot (biryani/pulao→raita, else→curd); the `curd_side` slot is displayed as "Curd / Raita" |
| `premium_menu_rule.py` | hard | broad premium min/max/day cap — **retired from the default ruleset** (rulebook §5/45-46); class kept for configs that still want it. Default now uses two `selector_frequency` exact-1 rules: `premium_veg_gravy_exactly_one` (`is_premium_gravy`@veg_gravy) + `premium_veg_dry_exactly_one` (`is_premium_veg_dry`@veg_dry) |
| `welcome_drink_buttermilk_rule.py` | hard | buttermilk (`is_buttermilk`) on exactly N (default 2) welcome-drink days, solver-chosen, non-consecutive |
| `theme_day_menu_rule.py` | soft | prefer theme-matched items per day |
| `theme_slot_filter_rule.py` | pre-filter | drop non-theme items on theme-heavy days (chinese/**continental**/biryani/south/north); config `exempt_slots` unioned with `EXEMPT_FROM_CUISINE`. The **bread cuisine lock** (south bread on south days, non-south otherwise) now honours `exempt_slots`; it used to run ahead of the exemption check in all three paths — `pre_filter_pool`, `diagnose` (`base in exempt_slots and base != 'bread'`) and `_project_filter_size` — so listing `bread` was silently ignored. Chennai lists it: its bread pool narrows to the 10 south-tagged rows (the dosai/idly family) on a south day, while the client actually serves chapati. Bangalore/Pune don't list it, so they are unchanged. **Cuisine exclusivity**: chinese/continental dishes appear ONLY on their own theme day, and only for cuisine-main slots (`_CUISINE_MAIN_SLOTS` = rice/veg_gravy/veg_dry/starter/nonveg_main); universal slots keep incidental tags. On a continental day the continental veg is the **gravy** — `veg_dry` is never continental (stays a normal Indian dish), so a continental day = continental rice/starter/nonveg/gravy + one Indian veg_dry. **`indian_veg_dry_themes`** (config, default empty) generalises that to any theme: a listed theme's `veg_dry` is narrowed to `north_indian ∪ south_indian` — both kept, so the objective picks whichever suits the day rather than the config pinning a region — and that theme's cuisine is dropped from `veg_dry` even on its own day. Tekion/Stryker/Stripe list `chinese`, so their Chinese Tuesday is chinese rice/gravy/starter/nonveg + one Indian veg dry. `exempt_slots` could NOT express this: `_filter_chinese` never consulted it (exemption worked only implicitly, via a slot being absent from `_CHINESE_FLAG_MAP`, while its `veg_dry` branch ran unconditionally — the same silent-ignore as the bread lock), and a blanket exemption would also switch off south/north/biryani narrowing. Wired in `pre_filter_pool` **and** `_project_filter_size`, or the pre-flight would report a phantom "0 items match the chinese filter" for a slot the solver no longer filters that way. **`slot_pool_by_theme`** (config, `{theme: {slot: selector}}`) is the only thing that OVERRIDES the canonical exemption, and it runs first and RETURNS — see note 41 |
| `theme_fallback_penalty_rule.py` | soft | penalty when theme cannot be met |
| `theme_starter_preference_rule.py` | soft | bonus for theme-matching starters |
| `item_cooldown_menu_rule.py` | pre-filter | ban recently used items |
| `week_signature_cooldown_menu_rule.py` | soft | avoid recent week signatures |
| `ricebread_gap_menu_rule.py` | pre-filter | enforce N-day gap |
| `nonveg_biryani_weekly_rule.py` | pre-filter | ≤1 nonveg biryani/week |
| `nonveg_dry_preference_rule.py` | pre-filter | prefer dry nonveg on the 2nd nonveg slot — **retired from the default ruleset** (superseded by the `slot_composition` 2-nonveg pair, which it conflicted with on chinese/biryani days); class kept for configs that still want the simple slot-2 dry heuristic |
| `ingredient_ban_rule.py` | pre-filter | per-client banned ingredients (case-insensitive exact match on `key_ingredient` **and** `primary_protein` — e.g. a mushroom ban catches both fields) |
| `selector_history_window_rule.py` | pre-filter (history) | **generic cross-week cadence**: a selector may recur only once per rolling `window_days` that is LONGER than the plan horizon ("fish once/15 days", "kadhi once/15 days", "oil-based bread monthly"). A single 5-day solve can't see prior weeks, so this reads saved history: `HistoryManager.selector_banned_by_date` finds the selector's last service and, for each planned date inside the window, bans **every** matching item — folded into the same `banned_by_date` the item-cooldown pre-filter already applies (no new solver machinery). `apply()` is a no-op; `matching_items(df)` resolves the selector against the city's ontology in `api.app`, and `_effective_history_window` counts `window_days` so the history query reaches back far enough. Pairs with a within-plan `selector_frequency max`/`daily_max` (this handles across-plans, that handles within-plan). Selector-level twin of the per-dish `item_cooldown`. Wired in the city rulesets (Bangalore special_sambar 15d; Pune kadhi/leafy 15d, oil-bread 30d) and per-client (Stryker fish/biryani/sambar 15d, Siemens kofta 14d) |
| `selector_frequency_rule.py` | CP-SAT | **generic Phase-1 rule type**: selector-driven horizon count (max/min/exact days, day-level) + **`max_per_week`/`min_per_week`** (per ISO calendar week — what a rule NAMED `*_weekly` has to mean, see note 26; `max` counts across the whole horizon and so silently tightens as the plan grows, `max: 1` becoming "once a fortnight" on 14 days. Both may be set: `max_per_week` for the cadence, `max` for a plan-wide ceiling; a `max_per_week` looser than `max` is rejected rather than silently taking the tighter one, and neither may be combined with `exact`. **`min_per_week`** is the floor and exists for the same reason `min` is not it — `min` counts days across the horizon, so "at least one a week" written as `min: 1` becomes "once a fortnight" on 14 days; each week's floor caps to the days that week can place, so a short week at either end relaxes instead of failing. Both keys replace the retired `item_frequency` rule type — see note 30) + `non_consecutive` + `daily_max` (per-day occurrence cap) + **`daily_min`** (per-day floor — the only way to say *every day* independent of horizon length, since `min` counts days across the horizon: `min: 5` is "5 of 5" on a week but "5 of 10" on a fortnight. Capped per day to what that day can place, so a thin day relaxes instead of going INFEASIBLE) + **`base_slot` may be a LIST** (a constraint that spans slots — "a protein source somewhere on the plate" is satisfied by the rice, gravy, veg dry, salad *or* dal, and scoping it to any one of them would be a different rule; a string still yields the single-slot behaviour every existing config relies on) + **`allowed_day_types`** (forbid the selector outright on days of other themes; skipped when the ban would empty a cell; **stands alone**, like `forbidden_weekdays` and for the same reason — "south-Indian bread only on a south day" is a complete rule with no count in it, and requiring one meant writing `max: 99`, which reads as a frequency cap nobody meant and becomes one on a long enough horizon). `allowed_day_types` is what keeps a themed dish on its themed day — a `mix` day is not narrowed by the theme filter at all, so a counter could serve biryani on Monday and none on its actual biryani day. plus **`forbidden_weekdays`** (a weekday-scoped ban, the twin of `allowed_day_types` for a rule that is about the calendar rather than a cuisine — TCL's "no baby corn, paneer or mushroom on Saturday and Sunday", where the weekend days carry no theme and `slot_day_restriction` would stand the whole slot down; same degrade-rather-than-fail path, and it stands alone as a constraint). Selector = flag/sub_category/item/key_ingredient/primary_protein/course_type/cuisine_family, plus `any_flag: [...]`, **`any_of: [selector, …]`** (the general "any of these", needed when one rule names several ingredients across both flag and text columns), **`all_of: [selector, …]`** (the conjunction: "an egg GRAVY" is `is_egg_dish` AND `is_nonveg_gravy`, and neither column alone says it — ICON Chn's Monday egg gravy came back as a boiled egg under the flag alone) and **`name_contains: [substring, …]`** (matches the dish NAME — the escape hatch for a family the ontology's columns file unreliably; `key_ingredient == 'baby_corn'` tags 67 Bangalore rows of which 3 are baby-corn dishes, it being the de-facto default for a mixed salad, while the 34 dishes actually named after baby corn carry `corn`/`bell_pepper`/`cauliflower`. Prefer a column when one is trustworthy). min/exact auto-capped to placeable (availability + non-consecutive aware) so it never forces INFEASIBLE. Config-driven in the per-city rulesets (`data/configs/city_rules/<city>.json`) |
| `attribute_grouping_rule.py` | CP-SAT + pre-filter | **generic Phase-3 rule type**: group a slot's candidates by an attribute (`group_by` = any column, e.g. item_color/key_ingredient) and constrain each distinct value: `non_consecutive` (same value not on adjacent days — rulebook 79 dal-colour), **`min_days_between: N`** (N CLEAR days before a value returns — `non_consecutive` is exactly N=1, and sixty configs say it, so both spell one `_gap`), and/or `max_per_group` (each value ≤N days/horizon — rulebook 82 sambar key-ingredient, an empty-history stand-in for the 15-day rolling window), plus **`max_cells_per_day`** (a value on at most N CELLS of one day — the *plate* constraint, and the reason it is applied to the raw literals rather than the day-bool the other keys use: that bool collapses "this value is somewhere today" to one variable and structurally cannot see a paneer gravy beside a paneer dry). **`base_slot` may be a LIST** (`_norm_slots`, same as selector_frequency/soft_preference — "the veg plate" is veg_gravy AND veg_dry together) and **`per_base_slot`** constrains each slot independently instead of pooling the day's cells. **`require_value`** drops candidates whose `group_by` cell is blank, standing down for any slot it would starve. See note 36 |
| `soft_preference_rule.py` | CP-SAT soft | **generic Phase-4 soft rule type** (objective-only, never INFEASIBLE): `mode` = **`prefer_cells`** (penalise every CELL that is not the selector — the per-cell twin of `prefer_daily`, and a separate mode because the two answer different questions: `prefer_daily` scores a DAY, so once one matching dish lands anywhere its penalty is zero and the other cells are unscored. Right for "a protein somewhere on the plate", useless for "make this day Tamil" — a hard floor of 3 over 5 slots paired with `prefer_daily` returned exactly 3 every time, measured. Takes `only_on_dates`. Tekion/Stryker want a non-dal protein on their 3 ordinary days hard and on the chinese/biryani days soft, because a hard every-day floor there would trade a whole plan for one dish. Symmetric, so a single mismatch scores twice; a day where one side carries none of the listed values is skipped entirely, or a chinese day would push the gravy off north AND south. | `slot_composition_rule.py` | CP-SAT | **generic Phase-3 rule type**: composes a slot family *per day*, switchable on the day's theme. `base_slot` + a self-gate on the counter's configured slot count: **`min_slot_count`/`max_slot_count` (preferred, a range)** or legacy `requires_slot_count` (exact). Permits repetition; never forces it (that's `fixed_daily_item`). Same `repeatable_item_flags()` hook, so `MenuSolver._declared_repeatable()` → `context['extra_repeatable']` feeds both consumers from one declaration. **`scope`** picks which exemptions apply: `both` (default, as above) or **`cooldown`** — the history ban stands down but `unique_items` holds, so the slot serves distinct dishes within a plan and repeats only once every distinct one is used. ### 4.4 `src/client/` — client config (Supabase, live reads)
- `client_config.py` → `ClientConfig` (dataclass, incl. `serve_weekends`), `ClientConfigLoader`, plus counter helpers `default_counter`, `normalize_counter`, `MAX_COUNTERS`. Per-category frequency is bounded by `_MIN_SLOT_COUNT`/`_MAX_SLOT_COUNT` (1..**5**); `customisation/multi_slot_editor.py` imports both so the editor can never offer a value the loader would clamp. The ceiling was 3, which made a real counter unconfigurable — a non-veg station serving biryani + gravy + dry + kebab + egg needs 5 `nonveg_main` slots and the editor answered "outside the allowed range". City: `AVAILABLE_CITIES` + `normalize_city`; a client's `city` is a plain `clients.city` column (not per-counter). `serve_weekends` is a plain `clients.serve_weekends` bool (Sat/Sun coverage). `item_cooldown_days` (`clients.item_cooldown_days`, nullable; None = `DEFAULT_ITEM_COOLDOWN_DAYS`=20) overrides the item-cooldown window per client. `is_launch_site` is a plain `clients.is_launch_site` bool (feature F, launch view): every existing client is false (the column defaults false), and a client created through the launch view is true — read/written via `get_client_is_launch_site`/`set_client_is_launch_site`, carried in `get_client_row`/`list_clients_with_city`, and an `is_launch_site` arg on `create_client`. `shared_categories` is a nullable `clients.shared_categories` JSONB (base slots synced across counters — the editor's toggle+multiselect; see note 22), read/written via `get_client_shared_categories`/`set_client_shared_categories` + a `create_client` arg, normalised by `_normalize_shared_categories_value` to known base/const slots. All read/written via `get_client_city`/`set_client_city`/`get_client_serve_weekends`/`set_client_serve_weekends`/`get_client_item_cooldown_days`/`set_client_item_cooldown_days`/`create_client(...)`. `AVAILABLE_THEMES` includes `continental` + the weekly-alternating `chinese_continental`.
- No in-memory cache; every read hits Supabase. Reads are **consolidated**: `get_client_row(name)` selects every config column in one query and `api.app._client_row()` memoises it on Flask's `g` for the request, so `GET /client-config` costs 1 round trip (was 7) and `/plan` 2 (was 6). `get_client_configs_from_row(name, row)` builds the per-counter `ClientConfig` list from an already-read row. Writes are **atomic**: `update_client_atomic(name, expected_version, fields)` applies every field plus the version bump in ONE conditional `UPDATE` (`WHERE name=? AND version=?`), replacing a bump-then-N-setters sequence in which a validation failure part-way left the row half-written with the version already incremented. `normalize_counters_for_write()` / `primary_counter_patch()` are the write-free validation halves used to check the whole payload before anything is persisted. `create_client()` is validate-then-insert for the same reason: it takes `working_days` and `source_pools` directly so they are part of the one INSERT — they used to be applied by follow-up setters *after* the row existed, so a rejected pool token answered 400 while leaving a real client behind with no pools (and the retry then failed on the duplicate name). There is no standalone version-bump helper: bumping `version` separately from the fields it guards is the ordering that bug came from, so `update_client_atomic` is the only write path.
- `ClientConfig.counter_name` records which counter a config came from, so per-counter rule overrides can be scoped. Supabase tables (consolidated to 4): `clients`, `app_settings`, `menu_history`, `week_signatures`.
- **F5 client item pools**: `clients.source_pools` (JSONB, nullable) stores the ontology `client`-column pool tokens this client draws from; `common` is implicit. `get_client_source_pools` returns `None` (column missing → callers use the full ontology), `[]` (unset → common-only), or the token list. `set_client_source_pools` normalizes/dedupes and strips `common`.
- Default day themes: Mon=mix, Tue=chinese, Wed=biryani, Thu=south, Fri=north.
- **Client config is one JSON document.** `clients.counters` (JSONB) is the single source of truth — an ordered, non-empty list `[{name, categories, slot_counts, theme_map}, …]`. `counters[0]` is the **primary** counter that `MenuSolver` plans from (`get_client` derives `ClientConfig` from it); extra entries are additional cuisine stations. `get_client_configs` yields one `ClientConfig` per counter — the API solves each independently (client-orchestrated: the planner calls `/plan` once per counter with `counter_index`), and the planner renders one table per counter (tabs) with per-counter regenerate/clear + a shared save/download. Mode is *derived*: `single` ⇔ 1 counter, `multi` ⇔ 2+. `get_counters_for_client` / `get_counter_setup` / `set_counters_for_client` / `update_primary_counter` read/write it. The old normalized `menu_categories` / `slot_count_overrides` / `theme_overrides` tables were folded into this column (premature normalization — config was always read/written per-client, never cross-client). The loader keeps a guarded `_legacy_primary_counter` fallback for a database that hasn't run `scripts/setup_all.sql` yet.

Ships without any model and is the permanent fallback whenever the model is off, unreachable or rejected. **`day_overview` is the primary surface and is a different shape from the rest**: four or five sentences of prose about what goes with what on this plate and what it lacks, built from `pairings` because those already name two dishes and a reason. `render_day` lists every verdict, which is right for someone auditing the ruleset and wrong for someone reading a menu — a column of `[ok] texture contrast` says nothing about the food. The overview never names a check or a rule (a test pins that), and a gap is stated in the same plain voice as a pairing rather than as a failed verdict |

**What `api/explain_llm.py::validate` guarantees, and what it does not** (note 35): every NUMBER, every snake_case WORD and every Title-Case PHRASE in the model's reply must appear somewhere in the pack, which makes a fabricated statistic or an invented dish structurally impossible. The Title-Case half was **missing, and the guarantee was overstated without it** — the snake_case check lowercases the prose and then looks for underscores, so it could never fire on "Paneer Butter Masala", a wholly invented dish written in the form `SYSTEM_PROMPT`'s own examples use; three such passed. Containment is word-ALIGNED in both directions (`_sourced_phrase`), because a plain substring test passes on anything: the pack genuinely carries one-letter words — the pairing summary "2 pairing(s) hold this plate together" harvests `s`, and `s` is inside `masala`. A single capitalised word is still unchecked (usually a sentence opener) and an all-lowercase phrase is undecidable, "the paneer gravy" possibly referring to a dish the pack does carry, so invention is caught in the form a model produces it rather than in every conceivable form. It does **not** police judgement — "only 3 textures, so the plate is a little soft" passes, because the 3 is sourced and *soft* is an opinion no rule can check. It DOES police **silence**: `_reports_the_bad_news` rejects a reply that says nothing about a failing CALIBRATED check, a `pairings.gaps` entry or a relaxed rule, because every other rule here catches only INVENTION and the cheaper failure is OMISSION — the easiest paragraph a model can write is the one saying everything is lovely, and it passed all of them. Rules 4/5/7-9 of `SYSTEM_PROMPT` told it not to and nothing enforced them; an unenforced instruction against flattery is worth very little. It cannot check that the prose is RIGHT, only that it is ABOUT the problem (one content word longer than three characters, `_COMMON_WORDS` excluded so "the" cannot satisfy it). Uncalibrated failures are deliberately NOT demanded — making the prose repeat a verdict we do not yet trust (note 33) would be the opposite of honesty — and a clean plate constrains nothing, since requiring hedging on a good day is its own dishonesty. That boundary is why the BULLETS are the primary surface and are gated on `checks.CALIBRATED`, with prose additive on top: the numbers a chef acts on come from Python either way. **The prose half has now run against a real model.** With a key configured, `gemini-3.1-flash-lite` returns an accepted overview in ~4s; the previously configured `gemma-4-31b-it` returns `model unavailable` or prose the validator rejects, because it writes its reasoning out loud before the answer — the capability probe the chef's-read doc asks for, run, with the default changed to match. The hand-written-prose accept rate (9 of 10) remains the only measure of how OFTEN a real reply survives `validate`; one accepted sample is not a rate.

Where `relaxations` come from: `src/menu_rules/relaxations.py` (note 31), which
is in the rules package rather than here because the stamp and the handler that
reads it have to stay together.

**Calibrated, not assumed**: `docs/explain_layer_calibration.md` scores all six
checks over 49 real menu days. Two (`spice_arc`, `richness_balance`) cannot fire
at their shipped thresholds — the observed data sits entirely inside the passing
window — and two more flag menus for obeying rules the client asked for. Read it
before tuning a threshold.

### 4.6 `src/` top-level
- `constants.py` — `REPEATABLE_ITEM_FLAGS_BY_SLOT` + `repeatable_row(row, base_slot)` (staple dishes: the SAME dish may recur daily in that slot, exempt from `unique_items` and the item-cooldown ban — the 21-day window governs ordinary dishes, not staples; keyed **by slot** because `is_tandoor` also marks tandoor breads, and a flat flag list let butter naan repeat all week in `bread`), `BASE_SLOT_NAMES`, `CONST_SLOTS`, `DEFAULT_OFF_SLOTS` (selectable-but-off-by-default: `curd`/`curd_rice` + combos), `COMBO_CATEGORIES` + `combo_minority_count` (dal_rasam/sambar_rasam/dal_sambar day-split), `DISPLAY_SLOT_NAME`, `DISPLAY_SLOT_ORDER` (single canonical order for the config editor + rendered menu — `slot_sort_key` and `slot_editor` both rank by it; welcome_drink→…→dessert→other veg→**nonveg_main last**, white_rice interleaved after rice), `NONVEG_PROTEINS`/`NONVEG_SLOT` (non-veg dishes may appear only in `nonveg_main`). Every combo key must also be in `EXEMPT_FROM_CUISINE` (its minority component is often a different cuisine that would otherwise be theme-filtered off on off-theme days).

- `settings.py` — the shared leaf: `SUPABASE_TIMEOUT_SECONDS`, `resolve_supabase_credentials()` (env only). Imports nothing of ours. The Streamlit entrypoint bridges `st.secrets` into the environment (`app.py::_bridge_streamlit_secrets`) so a `secrets.toml` deployment keeps working with the dependency pointing downward.

## 5. UI layer

### `ui/`
- `api_client.py` → `MenuApiClient` (HTTP wrapper used by Streamlit; no auth — endpoints are public). `explain(...)` calls `/api/v1/explain` and **must be passed the `relaxations` from the `plan()` response** — it cannot recompute them (note 31).
- `planner_view.py::flatten_result` keeps the **unflattened `solution`** and the plan's `relaxations` on the block alongside the rendered `plan`: `plan` is `{date: {slot: name}}` and `/explain` describes the plate, so it needs the per-slot attributes the flattening drops.
- `app.py` planner: a **"Why this menu" expander** per counter, behind a button — `/explain` is a second request and an optional one, so a user who never opens it pays nothing and a failure there can never cost a menu. **Five steps, in that order, because the order is the argument**: 1 the plate, 2 **what works together** (`src/explain/pairings.py` — the complements between named dishes, and the gaps), 3 how it balances (`CALIBRATED` verdicts only), 4 why THESE dishes, 5 what the solver could not fully enforce. Step 2 sits above the checks because a pairing names two dishes and a reason, which is actionable on its own, where '4 colours across 7 dishes' still has to be interpreted — and its `gaps` are never hidden or folded into the summary line, a hot curry with no yogurt being the one thing here a kitchen can fix this morning. Step 4 is stated ONCE at the top of the block rather than repeated under every day (twenty identical warnings read as noise) and is never hidden — a rule that bent is the one thing here a kitchen can act on. Per-day tabs, `st.metric` for the profile, and the raw renderer text still available under each day for copying. Two things the first version got wrong and this fixes: the plate now **marks which dishes the checks count** (● main / ○ condiment-drink-staple) because a reader seeing fourteen dishes above "Main dishes 7" has no way to tell which seven, which makes every number below look wrong; and a rule's `_comment` is cut to its first sentence with the RULE NAME leading, because `_comment` is the client's own words in some configs and 400 characters of developer rationale in others (`api.app._first_sentence`, `_NOTE_CHARS`).
- `formatters.py` → `format_item_html(item, is_nonveg=…)`, `flagged_slots_from_solution(sol, flag)` with its two named readers `nonveg_slots_from_solution` / `pinned_slots_from_solution`, `display_label_for_slot_id`, `THEME_TAG_COLORS`, `THEME_ICONS`.

Cells are selectable and "Regenerate selected" replaced the regenerate expander. Selection lives in the component, not session state, so picking six cells costs one rerun rather than six. `day_cells` is the pure plan-block → component-arguments shaping and is where the tests are; `cell_keys` is the ONE converter from the `{date: {slot}}` shape every projection returns to the table's `"<slot_id>|<iso>"` key, and `warned_cells` maps a WARNING diagnostic's `affected {date, slot}` onto every expanded cell of that base slot. Item colours come from `ui.theme_tokens.ITEM_COLOR_MAP` and are passed per cell as a spelled-out name plus a READABLE foreground (white prints `#555555`), never re-listed in the JS. `ui.planner_view.menu_table_html` is the superseded static renderer, kept as the fallback while the component is signed off.
- `formatters.py` also carries the two-service helpers (note 39): `dishes_from_solution` (what dinner must avoid) and `meal_difference` + `MIN_MEAL_DIFFERENCE` (how different it came out, measured and reported rather than constrained).
- `app.py` planner: **a failed generation clears `plan_blocks` first.** It used to `st.error(...)` and fall through, so the previous client's table stayed on screen under the new client's name and city — an Amadeus Pune header above a Bangalore counter's chicken/egg dishes, with stale Days / Slots / Total-items cards. The single-counter path now stores an `source: "error"` block (as the multi path already did), reruns, and the display short-circuits on it instead of rendering an empty table with live Save / Download buttons.
- `app.py` planner: sidebar has a single-select **City** filter (default "All", options = cities present among clients) that narrows the Client picker via `/clients` `clients_detail`; menu table renders non-veg dishes red (`.item-nonveg`, driven off `primary_protein` incl. egg); **Download Excel** (openpyxl, `_plan_xlsx`) — one sheet per counter, bold bordered headers, red non-veg; filename `menu_<client>_<date-range>.xlsx` (`_download_filename`). ## 7. Call graphs (typical flows)

### Generate menu
```
Streamlit app.py
  → MenuApiClient.plan()  [ui/api_client.py]
  → POST /api/v1/plan     [api/app.py]
    → @solver_gate                                      [api/concurrency.py]
    → ClientConfigLoader.get_client()                   [src/client/client_config.py]
    → ontology.repository.filtered_menu_data(city, pools)  [src/ontology/repository.py]
        (cached; ExcelReader → ColumnMapper → DataCleanser → PoolBuilder on a miss)
    → application.horizon / constant_items / history    [src/application/]
    → MenuRuleLoader.load_from_file()                   [src/menu_rules/menu_rule_loader.py]
    → HistoryManager (Supabase)                         [src/history/history_manager.py]
    → MenuSolver.solve()                                [src/solver/menu_solver.py]
        for each (day, slot): rule.pre_filter_pool()
        build CP-SAT model, add rule.apply() constraints
        optimize sum(get_objective_terms())
    → SolutionFormatter.to_dict()                       [src/solver/solution_formatter.py]
  ← JSON → Streamlit table
```

```
POST /api/v1/regenerate  [api/app.py]
  → MenuRegenerator.regenerate(base_plan, replace_mask)  [src/solver/regenerator.py]
    lock untouched cells, re-run MenuSolver.solve()
    rank by similarity_score()
```

### Save to history
```
POST /api/v1/save  [api/app.py]
  → HistoryManager.save() → Supabase (menu_history, week_signatures)
```

### Edit client config
```
Streamlit customisation/* → PUT /api/v1/client-config/<name>  [api/app.py]
  → ClientConfigLoader.update_*() → Supabase
  (live reads elsewhere; no restart)
```

## 9. Non-obvious design notes

1. **Cell-based CP-SAT**: one bool var per (day, slot, candidate) — enables per-item penalties and similarity-driven regeneration.
2. **Two-phase rules**: pre-filter eliminates items before the model is built (fast), then `apply()` adds CP-SAT constraints. When writing a new rule, decide which phase fits.
3. **No config cache**: `ClientConfigLoader` reads Supabase on every call — live edits, no restart. Don't add caching without thinking through invalidation.
4. **Dynamic worker allocation** in `api/concurrency.py`: 1 active solve → 9 workers; 2 active → 5 each. Tuned for ~1 GB RAM.
5. **Theme dispatch**: global weekday→theme map, per-client overridable via each counter's `theme_map` in `clients.counters`. Themes: mix/chinese/biryani/south/north/**continental** + **`chinese_continental`** (meta-theme resolved per ISO-week parity in `weekday_type_for_config` → even=chinese, odd=continental). Solver honors it via `theme_*` rules.
10. **Weekend service**: `clients.serve_weekends` — when set, `_weekdays_from` stops skipping Sat/Sun so plans cover them.
12. **Per-client item cooldown**: `clients.item_cooldown_days` (None=default 20). `api._apply_item_cooldown_override` rebuilds a fresh `item_cooldown` rule (never mutates the cached shared list) and the value is passed to `banned_items_by_date`; `_effective_history_window` widens the history query to match.
25. **No-repeat is HARD; the only escape is the declared-slot list, never a silent relaxation.** `ItemCooldownMenuRule.pre_filter_pool` removes every cooled-down dish outright and never "borrows back" a recent dish to fill a gap — if that empties a slot, `diagnose()` raises an **ERROR** and the fix is *more dishes in that category for that city*, not a quietly repeated menu. Repetition is permitted only where it is declared: `REPEATABLE_SLOTS` (`curd` — same dish daily), `COOLDOWN_EXEMPT_SLOTS` (`curd_side`/`curd_rice`/`soup`/`healthy_rice` — cycle through every distinct dish, then repeat), and per-dish staple declarations (`repeatable_items`, e.g. Pune's plain chapati). Deliberately NOT exempt: `rasam` and `sambar` — they are core dishes where a kitchen carries real variety, so they are fixed with data, not with a relaxation. A graceful-degradation variant (restore the least-recently-served dish rather than starve) was built and then reverted for exactly this reason: it made every slot silently repeatable, which is the opposite of the product rule. Sizing follows from the window: a strict count-1 slot needs roughly one distinct dish per working day in the cooldown window (~15 for the 21-day default) plus the week being planned.
17. **One item ontology per city, selected from `clients.city`** — the same shape the rules already had. `src/ontology/paths.py::city_excel_path(city)` (re-exported from `api/config.py`) resolves `data/raw/city_items/<slug>.xlsx`, falling back to `DEFAULT_EXCEL_PATH` (Bangalore) for a city with no file, so adding a city to `AVAILABLE_CITIES` never breaks planning. `MENU_EXCEL_PATH` still pins ONE workbook for every city (single-city deployments, tests) and then also switches off the per-city category declarations, because the file's contents no longer follow from the city name. **The caches are keyed by resolved path, not city name** (now `OntologyRepository`'s `_menu_data_by_path` / `_nonveg_by_path`, and `(path, pool tokens)` for `_filtered_by_path_and_pools` — see §4.5b; they used to be module globals on `api.app`): every city in `AVAILABLE_CITIES` has its own workbook today, so the sharing case is a city nobody has added a file for yet — it reads Bangalore's, and keying by city would hold two copies of a 6,000-row df — while keying the F5 pool cache by tokens alone (as it was) would hand a Pune client Bangalore's `common` pool. Everything derived from the ontology is city-scoped too: `repository.nonveg_items(city)` (Pune is all-veg, so nothing renders red) and `repository.item_names(city)` (a `constant_items` pin naming a dish only another city carries stays a stamped constant instead of becoming a candidate with no pool row). `/pool-preview` takes an optional `city`; `/editor-metadata` returns the union of tokens plus a `client_pools_by_city` breakdown, and `_validated_source_pools` validates against the city the client will have after the write.
15. **Client item pools (F5)**: the ontology `client` column tags each item with comma-separated pool tokens (exact-match, case-insensitive — never substring). A client's eligible universe = items in `common ∪ clients.source_pools`, deduped by `item_id`. `api._menu_data_for_client` filters the cached full df to that subset and rebuilds per-slot pools (cached per active-pool set) **before** `build_pools`, so the existing rule pipeline (theme/cooldown/ingredient_ban/…) runs on the merged pool — a borrowed item still obeys the target client's rules. `common` (always included) covers every mandatory slot, so filtering never empties one. When `source_pools` is `None` (pre-migration/column missing) the full ontology is used (unchanged behavior). **`FULL_POOL_CITIES`** (`src/constants.py`, checked first in `filtered_menu_data`) lists cities where the narrowing is switched off entirely and **every** client plans from the whole city list: **`bangalore`** (only 893 of 4,349 rows carry `common`; the other 3,456 sat in eight client pools while most clients had `source_pools=[]`) **`ncr`** (no `common` pool at all — all 1,630 rows tagged to one of eight sites: stryker 504 · carelon 443 · junglee games 353 · airtel noida 273 · sinch 247 · siemens 223 · sael 203 · corning 124, plus 93 untagged) and **`chennai`** (191 of 673 rows in eight per-site pools while three of the four new clients have `source_pools = []` — World Bank could not see the 21 rows tagged "World Bank", and TCL, which serves a veg biryani daily, could reach 4 of the 14 veg biryanis). NCR already reached the full list, but only via the empty-subset fallback below; naming it here makes that intentional and also keeps the whole list for a client who *does* set `source_pools`. **`hyderabad`** joined for the sharpest version of the same problem: its pool tags name the WRONG CITY. `hyderabad.xlsx` was seeded from Bangalore's list, so ~5,300 of its 6,260 rows carry a Bangalore client's token (healthineers/citrix/booking.com/…) — sites in another city that no Hyderabad client will ever select — leaving `common` at 960 rows and none of Quest's 101 additions, every one of which is tagged `quest`. It is a city-level switch on purpose — reversible in one line, no client row touched. **The check is on the RESOLVED workbook, not the city string** (`Path(city_excel_path(city)).stem`): a client whose `clients.city` is null reads Bangalore's list — that is what `city_excel_path` falls back to — but `normalize_city(None)` matches nothing, so it used to be denied Bangalore's *policy* and planned from `common` alone, roughly a fifth of the list, while reading the file the other four fifths live in. Stripe is one of five null-city clients (`scripts/backfill_client_city.sql`), and the effect was that every dish its own menu import had just added was invisible to it. Keying by resolved path is what the caches above already do (note 17): one identity, one policy. **No-`common`-city fallback** (the mechanism NCR used to rely on): a client whose eligible subset comes out **empty** falls back to the full city list rather than planning from nothing. And the city required-slot check is **not** applied to a filtered subset — it is ontology-integrity (enforced on the full list by `menu_data`); a slot a client's pool cannot fill surfaces per-counter in `diagnose`/the solve, not as a build-time 500. Per-client *rules* keyed to the pool identity are intentionally out of scope for now.
16. **Two-nonveg daily composition + theme-filter union**: the base ruleset's `slot_composition` rules (`nonveg_main_daily_pair`, `veg_dry_north_south_pair`) compose a counter's *pair* of nonveg mains / veg dries per day by theme. They self-gate on `requires_slot_count`, so single-slot counters are unaffected. Crucially, `ThemeSlotFilterRule` normally narrows `nonveg_main` to one cuisine on chinese/biryani/south/north days (chinese-gravy-only, biryani-only, …), which would delete the paired north/south chicken gravy before the solver sees it. So `_augment_nonveg_pair` (theme_rules.py) keeps `themed ∪ north/south-chicken-gravy` for `nonveg_main` **only when `cfg.slot_counts['nonveg_main'] >= 2`** (`_has_multi_nonveg`); single-nonveg counters keep the strict themed pool. It also keeps `_NONVEG_STRUCTURAL_FLAGS` (dry / tandoor / egg): the filter's job is to guarantee the *themed* dish is available, not to make every dish themed, and narrowing a 5-dish station to biryani + chicken gravy left it 0 dry and 2 egg items against a composition wanting one of each daily. The themed dish is still guaranteed — the composition rule mandates it. The composition rule then places one themed dish + one regional gravy. That retention used to start at **>= 3**, which left the same hole at 2: Bakertilly's "only on biryani day we will have chicken dry" needs a dry available on its biryani day, the narrowed pool held none, and the component silently dropped so Wednesday came back biryani + gravy. Widening at 2 cannot change what the **default** ruleset produces — with two cells and `nonveg_main_daily_pair` mandating the themed dish plus a regional gravy, both cells are already determined — it only lets a client that overrides that composition have its second dish be available.
19. **One staple declaration, four consumers.** `repeatable_item_flags()` → `MenuSolver._declared_repeatable()` → `context['extra_repeatable']` is read by `unique_items.apply()`, `item_cooldown.pre_filter_pool()`, `slot_composition._horizon_limited_components()` and (via `_peer_rules`, since diagnose() has no context) `unique_items.diagnose()` + `item_cooldown.diagnose()`. Each one that misses the declaration fails differently and quietly: the cooldown starves the slot a week later, the composition swaps a daily mandate for a floor of one ("chapati daily" → "chapati once"), and diagnose() reports a shortfall the solver will not hit. When adding a rule that reasons about "how many distinct items does this need", wire it to the declaration.

20. **A one-slot `slot_composition` component IS "this slot must be a matching dish".** `sum(matching vars on the day) >= count` over a family with one cell and `count: 1` leaves the cell no choice. That is the primitive for "chapati daily in indian bread" and "welcome drink will have buttermilk daily". `fixed_daily_item` is a *different* rule and the wrong tool for it: it only makes the matching dish CONSISTENT across days and leaves the solver free to serve a non-matching dish instead (Amadeus Pune got phulka). Use `fixed_daily_item` when something else already mandates the dish and you want it to be the same one; use a composition component when you want the dish. **But a component is a FAMILY, and a STAPLE is one dish** — the client's words are "staple means like white rice and pickle, it should be the same daily". "Chapati as staple" written as a component over `is_plain_phulka_chapathi` serves a chapati every day and a DIFFERENT one each day: ten Pune breads including `beetroot_chapati` and `jeera_roti`, 36 Bangalore ones for DXC, 12 Chennai ones for ICON Chn. It loads, it solves, and it reads right in review. A staple belongs in `constant_items` — a daily string, or a weekday map when it is a staple only on some days, which leaves the others to rotate. A component is right when the client named a CATEGORY ("always a wheat or maida flat bread, never the dosai/idly family"). `tests/clients/test_staples_are_one_dish.py` holds the line: a composition whose comment claims a daily dish must resolve to exactly one, or be listed there as a family with the client's own sentence.

18. **Staple-ness is regional, so it is declared by a rule, not a constant.** `REPEATABLE_ITEM_FLAGS_BY_SLOT` (constants) is global and correct for the chicken kebab; the new `repeatable_items` rule type puts the same declaration in a **city or client** ruleset. Pune's rulebook R36 states plain chapati/phulka may run on consecutive days — its bread pool was exactly those two dishes, so under the 21-day cooldown week 2 would have no bread at all — while a Bangalore bread slot rotating naans and parathas wants the no-repeat rule intact. **Keep the selector as narrow as the client's sentence**: an exemption is permission to repeat EVERY DAY, so it must not be phrased in terms that something else may legitimately widen. R36 and Chennai's twin selected on `is_plain_phulka_chapathi`, and `bread_form_flags.py` correctly widening that flag (Pune 2 → 9 rows) would have licensed a beetroot chapati daily — a no-repeat exemption growing as a side effect of a data correction. Both now name the two dishes. Both consumers read one declaration: `MenuSolver._declared_repeatable()` → `context['extra_repeatable']`, which `unique_items` folds into its repeatable set **and** (new) `item_cooldown.pre_filter_pool` exempts from history bans. Wiring only unique_items is the trap: the exemption then reads as applied while the cooldown still starves the slot a week later. `ItemCooldownMenuRule.diagnose()` reads the same declarations via `_peer_rules` so the pre-flight report and the solve agree — without that, a 2-item bread slot with both dishes in history is reported as a blocking ERROR the solver would not have hit.
13. **Colour variety is dynamic + diagnosable**: its numbers now come from the city ruleset (`color_variety` rule → `solver_overrides()` → `SolverConfig`); Bangalore ships none and keeps the defaults below. The built-in colour rule (`MenuSolver._add_color_constraints`) clamps `min_distinct` to `min(configured, colour-slots-configured, **colour-cells-this-day**, colours-present)`. The per-day cell count is the one that is easy to miss: `skip_cells` removes cells the config still counts, so a day serving 2 of its 5 colour slots was asked for 3 distinct colours (Amadeus Pune's Sunday). Colours-present cannot catch it — colours available and cells available are different numbers so small counters (e.g. a 2-slot Chinese station) aren't trivially INFEASIBLE. `diagnostics.color_variety_diagnostics` pre-flags the *provable* residual (`colours_available × max_same_color < colour_cells`) as an ERROR before the solver runs. **Asymmetric per-colour cap (rulebook 89-91)**: every colour ≤ `max_same_color_per_day` (=2, rule 90) EXCEPT up to `max_colors_at_reach` (=1) colour may reach `max_same_color_reach` (=3) — encoded as `sum(colour) <= soft_cap + (reach-soft_cap)*b` with a reach-bool `b` and `sum(b) <= max_colors_at_reach`. Rice≠gravy colour holds unless `ignore_rice_gravy_color_diff_on_chinese_day` (rule 92); colour-counted slots = `cfg.color_slots` (excludes white_rice/curd, rule 93).
14. **Solver time budget is a total, not per-attempt**: `MenuSolver.solve` enforces a wall-clock `deadline` across the ≤8 restart attempts (each capped at `min(slice, remaining)`), so `time_limit_sec` bounds total wall-clock (was `max(20, total/8)` × 8 ⇒ up to 160s for a 60s request).
11. **Optional/combo categories**: `curd` (plain-curd station, pool from `is_plain_curd`; in `REPEATABLE_SLOTS` so it's exempt from unique_items + cooldown and may recur daily), `curd_rice` (pool from `is_curd_rice` flag) and combos `dal_rasam`/`sambar_rasam`/`dal_sambar` (dal majority) are base slots in `DEFAULT_OFF_SLOTS` (selectable, off by default). **`curd_side` (Curd/Raita), `curd_rice`, `soup` and `healthy_rice` are in `COOLDOWN_EXEMPT_SLOTS`** — exempt from the 21-day item-cooldown ban but, unlike `REPEATABLE_SLOTS`, they KEEP `unique_items`, so they still serve distinct dishes within a week and only repeat once every distinct one is used (freshness rotates least-recently-served first — "after a whole cycle"). These condiment/side slots have small pools (2-13 distinct); a rolling multi-week sweep found the hard cooldown drained them empty by week 2-3 and turned the solve INFEASIBLE on ~18 counters. The cross-week no-repeat window is wrong for a side, so only the *ban* is dropped (pan-India); wired in `ItemCooldownMenuRule.pre_filter_pool`/`diagnose` alongside `REPEATABLE_SLOTS`, `test_curd_categories.py::TestCurdSideCurdRiceCooldownExempt` pins it. Complementary data fix: the deleted `expand_side_pools` step adds 7 new veg dishes to each of `healthy_rice`/`dessert`/flavoured-chapati `bread`/`starter` in every city (Pune had 1 healthy rice, 0 starters), so the non-exempt of these (dessert/starter/bread) have enough distinct dishes to survive too. `curd` and `curd_side` (displayed "Curd / Raita") are the two yogurt-side options and are mutually exclusive per counter (`MUTUALLY_EXCLUSIVE_SLOT_GROUPS`, enforced in `ClientConfigLoader._validate_counters`); `curd_rice` is independent. Combos split one slot across the week by course_type (majority/minority via `combo_minority_count`, applied per-day in `MenuSolver._build_cells` via `_combo_day_variant`). **The two components ALTERNATE** — client rule: "when the combined slots are used it should alternate". The minority used to fill the LAST `combo_minority_count(n)` days, so a working week ran dal/dal/dal/sambar/sambar; `_combo_minority_days` now spreads it evenly, giving dal/sambar/dal/sambar/dal. The counts are unchanged and the split is still deterministic by day index (regenerate stability); because `combo_minority_count` keeps the minority at or under half the horizon, an even spread can always avoid two minority days in a row, which `test_menu_solver_helpers.py` pins as a property across all three combos and every horizon length 2-21. Optional slots are skipped by the mandatory-pool validation. A combo must be listed in `EXEMPT_FROM_CUISINE` or its minority component (often a different cuisine) gets theme-filtered out on off-theme days and the split silently collapses to all-majority.
6. **History split**: `menu_history` is one JSON document per client-day (`menu={slot:item}`), exploded to item-level in memory for cooldowns; `week_signatures` is a weekly hash for week-level cooldowns.
7. **Supabase is the source of truth** for clients, history, overrides — Flask and Streamlit both read it directly.
8. **Slot expansion**: base slot names like `veg_dry` get expanded to indexed slots `veg_dry__1`, `veg_dry__2` in `PoolBuilder._expand_slots_in_order`. Rules operate on expanded names.
9b. **Per-counter rule scoping**: a `client_rules.json` block may carry a `counters` map — `{"counters": {"<counter name>": {disable, rules, constant_items}}}` — layered over the client-level entry. A rule that only applies to one station (L&T's `Non Veg Lunch` is themed biryani daily, so the weekly nonveg-biryani cap is dropped there) stays scoped instead of silently switching off for the client's other counters. `load_for_client(client, generic, counter_name)` and `get_client_constant_items(client, counter_name)` take the counter.
9c. **Rules are never relaxed just to return a menu**: an over-constrained counter fails with a message naming the tightest slots, because the useful output is the conflict, not a plan that abandoned the rules. The single exception is *provable arithmetic impossibility* — a slot with fewer distinct eligible items than days to fill (`unique_items_menu_rule.starved_slots`) — where uniqueness is lifted for that one slot only, a HIGH-tier repeat penalty still maximises variety, and `diagnose()` reports it. Frequency targets cap to `min(placeable_days, distinct_matching_items)`: counting placeable days alone asked for two liquid desserts from a pool holding one. Every config-driven rule type (`selector_frequency`, `slot_composition`, `attribute_grouping`, `unique_items`, `curd_side`) implements `diagnose()`, so an inert or under-enforced rule is reported rather than silently dropped. Worked example of why the exception is arithmetic and not a fallback: `common` holds exactly 4 distinct `curd_rice` items, so a common-only client running that station over 5 days must repeat one. The other 9 `curd_rice` items in the ontology are client-specific health variants (millet / brown-rice / dry-fruit) belonging to `healthineers`/`continental`/`cloudera` — attaching one of those pools to fix the count would import a whole unrelated client's menu, so the right resolution is a 5th `common` item, which is what the diagnostic asks for.

9e. **A frequency cap can be *forced* past, and that must be detected, not discovered as INFEASIBLE**: `max`/`max_per_week` was assumed "only tightens, never wrong". It is wrong whenever the counter cannot avoid the selector on more days than the cap allows, and there are two ways that happens — the theme filter leaves the slot nothing else (`SelectorFrequencyRule._forced_days`), or a `slot_composition` mandates a matching item (`slot_composition_rule.days_forced_by_composition`, cross-checked via `_peer_rules`). Both are provable from the pools, so they are ERRORs and `/plan` answers 422 naming the rule, the day count and three concrete fixes. Worked examples: Amadeus's Chinese counter is themed `chinese_continental` every weekday, so on an odd ISO week all five days resolve to *continental* and the theme filter narrows `rice` to continental rice — five forced days against `continental_rice_weekly`'s `max: 1`, INFEASIBLE on 9 of 14 start dates while `/diagnose` said `would_succeed: true`. Siemens Technology's non-veg counter is the composition variant: two biryani-theme days each get a mandatory biryani against `nonveg_biryani_once_per_week`. Note `max` counts **days**, not dishes — a counter with 2+ nonveg slots could satisfy the weekly cap by stacking two biryanis onto one day, which is what `nonveg_biryani_one_per_day` (`daily_max: 1`) exists to stop.

9g. **Some dishes are staples, not variety slots — model that instead of relaxing the rule that wants them daily**: L&T's 5-dish non-veg station needs a kebab every day, and only one kebab is eligible for a common-only client. Read as an ordinary dish that is a five-distinct-items shortfall; read correctly, the chicken kebab is a **staple** like steamed rice — the same dish daily — so it is exempt from `unique_items` and the cooldown ban and one item covers the week. That is what `REPEATABLE_ITEM_FLAGS_BY_SLOT` encodes. Separately, `_horizon_limited_components()` + `_add_horizon_floors()` still handle a *genuine* shortfall in a non-staple component (distinct items < days it is required, which per-day availability never reveals) by replacing the per-day mandate with an at-least-N-days floor via `OnlyEnforceIf` indicators — same bug class as the `selector_frequency` distinct-items cap (note 9c), one rule type later. A staple component is skipped by that check entirely.

9f. **Sweep more than one start date**: `chinese_continental` resolves per ISO-week parity, so satisfiability is date-dependent and a mid-week start spans two ISO weeks (the theme flips inside a single horizon). The all-clients sweep originally used one Monday of an even week and passed Amadeus's Chinese counter while it was failing on most real start dates. `test_every_counter_generates_on_other_start_dates` covers an odd-week Monday and a Wednesday, and accepts 200 **or** a 422 that names a rule and a fix — an unexplained 500 is the failure it exists to catch.

21. **The load path is already city-scoped and lazy — measured, not assumed.** Caches start empty; one Chennai `/plan` loads exactly ONE dataset (`chennai.xlsx`, 361 rows, 22 MB peak heap) and never touches Bangalore's 6,143-row master. `/clients`, `/client-config/<name>` and `/health` load **zero** datasets (1-2 ms). `/diagnose` and `/pool-preview?city=` load one (0.4-0.6 s cold). So "city → that city's dataset → that client's rules" is what the code does; there is no eager whole-ontology load to remove.

23. **Cadences longer than the plan horizon are enforced from saved history, not within one solve.** A 5-day plan cannot see prior weeks, so "once per 15 days / fortnightly / monthly" rules can only be enforced by reading `menu_history`. `selector_history_window` (note in §4.2) is the mechanism: `api.app` resolves each such rule's selector to concrete item names against the city's ontology (`matching_items(df)`), passes `(items, window_days)` pairs to `_build_history_context`, and `HistoryManager.selector_banned_by_date` bans the whole family on any planned date within `window_days` of a saved occurrence — merged into the SAME `banned_by_date` the item-cooldown pre-filter already applies (so no solver change). It pairs with a within-plan `selector_frequency max`/`daily_max`: the window handles ACROSS plans, the cap handles WITHIN one. `_effective_history_window` now also scans `window_days`, so a 30-day monthly cadence widens the history query. **`matching_items` is scoped to `base_slot`** (by `course_type`) when one is set: "leafy veg_dry once per 15 days" must not fire because a leafy *dal* was served last week — matching by flag alone banned the whole family across every slot and starved Pune's dal the week after a leafy dal was saved. A fresh plan (no history) is never affected — the ban only triggers on a real prior occurrence, so this can't make a first-week plan INFEASIBLE. This is the selector-level twin of the per-dish `item_cooldown` (which is why they share the ban map). Applied across every city (Bangalore/Pune) and the NCR clients that stated such cadences. Week-level co-occurrence ("biryani not the same week as fish") is now handled separately by `same_day_exclusion` with `"scope": "week"` (Stryker NCR), a within-plan constraint rather than a history read; the positive "serve it once per N days" direction stays deferred.

24. **Menu variety is a soft freshness objective, not a longer cooldown.** The hard item cooldown (default 20 days) only *bans* a dish for a window; the moment it lapses nothing stops the solver reprinting day-1's menu on day 21. The fix is a preference, not a longer ban: `HistoryManager.days_since_last_served(as_of, const_slots, repeatable_items)` builds `{item_base: days-since-last-served}` from saved history (staples that recur by design are excluded — steamed rice, the daily kebab), `_build_history_context` returns it as its 4th value, and it is threaded through `SolverInputs.recency_by_item` into `MenuSolver`/`MenuRegenerator`. `MenuSolver._freshness_bonus(item)` = `min(days, FRESHNESS_CAP_DAYS=30) * FRESHNESS_UNIT=3000` (a dish absent from the map — never served in the window — scores the full cap), added per candidate in `_build_objective`. The weights are deliberate: `CAP*UNIT` (90k) sits **below** one LOW soft-rule unit (1e6, `OBJECTIVE_TIER_WEIGHTS`) so any real rule still outranks freshness in a cell ("unless a rule is forcing it"), while `UNIT` (3000) sits **above** the random tie-break (max ~1000) so freshness actually orders candidates; ties among equally-fresh dishes fall back to the tie-break, preserving cross-solve variety. It never bans, so it can never make a solve INFEASIBLE, and an empty recency map (regenerate paths / tests) yields 0 bonus — historic behaviour. Pairs with the existing within-plan `unique_items` (no repeats inside one horizon) and `week_signature_cooldown` (avoid recent whole-week signatures): together they spread item usage as far as the pools allow. `test_freshness_variety.py` pins the recency map, the bonus bounds, that the least-recently-served candidate wins an unconstrained cell, and that an all-recently-served map never forces INFEASIBLE. **`REGEN_SIMILARITY_PENALTY` is derived from the cap, not written as a literal**, because the two pull on the SAME dish: `MenuRegenerator` first tries to forbid the dish being replaced and falls back to a penalty when the hard block would empty the cell, and the dish it is penalising is usually the one freshness likes most — a dish absent from the recency map scores the full cap, and absent is the common case since the map holds only what has been saved. At the historic `-10_000` against a `+90_000` cap the arithmetic was not close: the solver re-picked the dish the user had just asked to replace and the button appeared to do nothing. Now `-3 * MAX_FRESHNESS_BONUS` (-270k) — a clear margin over freshness, still an order of magnitude under one LOW unit so the rule tiers are untouched and a soft preference can still keep a dish in place. `TestRegenerateOutbidsFreshness` pins it as an *ordering between the two constants*, so tuning either cannot quietly re-open it.

22. **Cross-counter common categories are a client-orchestrated pin-from-primary pass, not a joint solve.** A client declares `shared_categories` (a list of base slots) — from the **editor** (`clients.shared_categories`, a nullable JSONB column; the multi-counter editor shows a toggle + a multiselect of slots present on 2+ counters) **or** from `client_rules.json` (`MenuRuleLoader.get_shared_categories()`, e.g. DXC). `GET /client-config` returns the DB value when set and **falls back to the file value** otherwise, so both sources feed the same planner path. Config layer mirrors `source_pools`: `get/set_client_shared_categories`, `_normalize_shared_categories_value` (keeps known base/const slots only), threaded through `get_client_row`/`create_client`/`update_client_atomic`/`_apply_fields_individually`. The planner (`app.py` multi-counter loop) solves the **primary** counter (index 0) first, extracts its dish for each shared base slot per day via `ui.formatters.shared_items_from_solution` → `[[iso_date, slot_id, item], …]`, and passes them as `shared_items` to every later counter's `/plan`. Server-side, `api.app._merge_shared_items` folds them into `forced_items` — the SAME narrow-the-cell mechanism a `constant_items` pin uses (note 9), so every other rule still sees the pinned dish. An explicit client constant already in `forced_items` **wins** (a sibling counter never overrides the client's own config); a shared item that is not eligible for the target cell is logged and the cell solves normally (never INFEASIBLE from the sync). Non-shared slots (e.g. a non-veg station's `nonveg_main`) still solve independently. DXC uses it for bread/rice/sambar/rasam/curd_side/dessert/white_rice. **A counter may opt OUT**: `shared_categories_excluded_counters` in the client's rules file (`MenuRuleLoader.get_shared_category_exclusions`, surfaced by `GET /client-config`, read by the planner, which simply sends that counter no `shared_items`). File-only, no DB column and no editor control, because it is a statement about the menu's structure like the rules beside it. ICON Chn needs it — "rice combo counter is not linked to the shared items list it has seprate menu" — and `clients.shared_categories` is otherwise all-or-nothing per client. Remaining limits: (a) it makes the PRIMARY the source of truth rather than optimising all counters together (docs/client_logics.md gap 1); (b) the source is always the primary, so "the same non-veg on counters 2 and 4" — ICON Chn again — cannot be expressed at all. Naming a source counter per shared slot is the change that would cover both.
    **`/editor-metadata` used to be the one exception** — it loaded EVERY city (3 workbooks, 4,956 rows, 4.8 s cold) because `_city_pool_tokens()` loops `AVAILABLE_CITIES`. Now **12 ms cold, zero datasets**: the answer is a handful of strings per city, so the deleted `build_pool_token_map` step commits it to `data/raw/city_items/pool_tokens.json` and the endpoint reads that, falling back to the workbooks when the file is absent (a fresh checkout is slow, never wrong). `_city_pool_tokens(only_city=...)` also scopes the work when a city IS known, and `ui.api_client.get_editor_metadata(city=...)` can pass one. Read by `src.ontology.paths.pool_tokens_for_city`, which opens the JSON itself rather than importing the script that writes it: `api/app.py` used to `from scripts.build_pool_token_map import tokens_for_city` inside a bare `except`, so when the scripts moved the import started failing and the endpoint silently went back to parsing five workbooks — a degradation indistinguishable from a cold cache. Staleness is the price of a derived artefact; `the deleted build_pool_token_map step --check` recomputes from the workbooks and exits 1 on disagreement (CI runs it), and `test_pune_integration.py` asserts the endpoint opens no workbook at all and answers identically with the map forced off. Historic detail (3 workbooks, 4,956 rows, 4.8 s cold / 23 ms warm) because `_city_pool_tokens()` loops `AVAILABLE_CITIES`. Reading only the `client` column is NOT a fix: openpyxl parses the whole sheet regardless, measured at 1.1x.
    **No unused API surface**: 14 of 15 endpoints have a UI caller; `/api/v1/metrics` has none by design (Prometheus scrape).

9d. **Diagnostics are aggregated per slot, not per (day, slot)**: `theme_slot_filter`'s narrowing INFO fired once per themed day per slot — 811 entries across the 56 counters the fleet had then, each captioned "No action needed" — which buried the 10 real WARNINGs. It now emits one line per slot carrying the day count and the resulting pool range (283 entries, same information). When adding a `diagnose()`, aggregate before appending: the list is read by a human deciding whether to fix data.
9. **Per-client custom rules**: `customisation/client rules/<slug>.json` — one file per client — stores per-client overrides keyed by client name (the single 2,453-line `client_rules.json` was split; the loader still falls back to it when the directory is absent). **The key must equal `clients.name` byte-for-byte** — the lookup is exact-match with no normalisation, and a mismatch is silent: every rule for that client loads as zero, `/diagnose` still reports clean, and a plausible-looking plan comes back having ignored all of them. `ToastTab CHN` was configured in the DB while this file said `Toast Tab CHN`, and the only symptom was white rice on a north day. Shape is `{disable: [city_rule_names], rules: [...], constant_items: {slot: value|{weekday: value}|[a, b]}}` (legacy bare list still works as `{rules: list}`). A `constant_items` value that is a **list alternates across ISO weeks** (even week → first, odd → second, index = `iso_week % len`, the same parity `chinese_continental` uses), usable bare (alternate every day) or as a weekday-map value (`{"wed": ["Hyd Mutton Biryani", "Fish Tikka Masala"]}` → Wednesday only, mutton one week / fish the next — Siemens Technology's non-veg counter). Resolved in `_resolve_client_constant(spec, weekday, iso_week)`, threaded from both the forced-item build (`api.app`) and the post-solve stamp (`menu_solver`) so the two agree. `load_for_client()` merges by rule `name` via the same `_merge_rule_dicts` used for city `extends` — same name overrides, `disable` drops. `constant_items` are honoured **two ways, chosen by whether the dish exists in the ontology**: a pin naming a real item becomes `SolverConfig.forced_items[(date, slot_id)]` and its cell stays in the model with candidates narrowed to that dish, so every other rule sees it (its colour counts toward colour variety, its cuisine toward cuisine variety, and unique_items stops a duplicate elsewhere); a pin naming a dish the ontology does not carry ("Mutton Biryani", "Fish Tikka Masala" — the ontology holds only chicken + egg for non-veg) has nothing to narrow to, so its cell is skipped and the text is stamped verbatim post-solve. Adding the dish to `menu_items.xlsx` switches the same pin over to the solver with no config change. Mutually-exclusive sibling slots are removed either way. **A pin may also be a FIXED ITEM the counter serves without a station** — a daily curd, papad or welcome drink is served every day and never chosen, so requiring a rotating category for it was asking the operator to configure a station that does not exist. `_resolve_constant_items` drops a pin for an unserved slot only when it is AMBIGUOUS, i.e. the client has other counters the pin might have belonged to; it is kept when the client has one counter (`ClientConfig.counter_count`) or the pin sits in that counter's own block (`MenuRuleLoader.get_counter_scoped_constant_keys`). The second half is in `_rules_and_skip_for_client`: only a slot the counter actually SOLVES may be forced. `pools` holds every slot the ONTOLOGY can fill, so a kept pin used to match a real dish, land in `forced_items`, and then be dropped by BOTH paths — no cell to narrow, and the post-solve stamp skips anything in `forced_items` as already placed. Booking.com's daily curd vanished exactly this way, as did Telstra's and Tessolve's curd, H&M's welcome drink and Quince's and Sinch's raita. `api._canonical_item_name` does the space/underscore matching. Client `working_days` (DB column) filters the plan horizon (e.g. Quince = Wed/Thu/Fri).

26. **"Weekly" has to mean weekly on a plan longer than a week.** `selector_frequency`'s `max` counts days across the WHOLE HORIZON. That is right for a one-week plan and silently *tightens* as the plan grows — `max: 1` means "once a fortnight" on 14 days and "once in three weeks" on 21 — and sixty shipped rules were named `*_weekly` / `*_once_per_week` while behaving that way. `max_per_week` is the addition: the same count bucketed by **ISO calendar week** (Monday-Sunday, the boundary `chinese_continental` already resolves its parity on — a calendar week, not a rolling 7-day window, so a Thursday and the following Monday are legitimately different weeks). `max` keeps its meaning, so a rule that really is "once per plan" can still say so. `nonveg_biryani_weekly` was the sharpest case because its key was **already called `max_per_week`** while summing over the horizon — the name promised the semantics and the code did not deliver them — and it is the most easily contradicted: a biryani-theme day narrows a single-nonveg counter to biryani only, or `nonveg_main_daily_pair` mandates one, so the second biryani day is FORCED rather than chosen and the cap then reads as impossible. **Two halves have to agree** (`tests/rules/test_per_week_caps.py` reads the source to check both): `apply()` constrains per ISO week, and `diagnose()` buckets the forced days by week and compares the busiest one. Comparing a horizon total against a weekly number is what made a satisfiable rule report as impossible; comparing per-week while constraining per-horizon would hide a real conflict. That is also why `slot_composition` gained `dates_forced_by_composition()` — the old `days_forced_by_composition()` returned a COUNT, and a count cannot be bucketed by week, so the per-week check had nothing to work with and fell back to the horizon total. The effect was fleet-wide: at 7 days 74 of 85 counters diagnosed clean, at 14 days only 34, and almost every block named one of these rules; with per-week caps it is 85 of 85. Sixty configs were migrated `max` → `max_per_week` and a test fails if a `*weekly*`-named `selector_frequency` rule goes back to `max`.

30. **Two rule types must never share a config key.** `item_frequency` was a second, older frequency rule whose `min_per_week`/`max_per_week` **summed over the whole HORIZON** — the same defect note 26 fixed in `selector_frequency` and `nonveg_biryani_weekly`, surviving in the one type that was not touched, and with the keys again NAMED for a week. Two configs used it: Tekion and Tekion CHN, both "one liquid rice a week". On a 25-day plan that read as one liquid rice in five weeks, while `tekion_chn_khichdi_thursday` — a `slot_composition` — forced one every Thursday; the config's own comment ("caps liquid rice at one a week, so pinning Thursday lands that one there") shows the intent was per-week throughout. It was also strictly weaker: five selector keys against `selector_frequency`'s thirteen, with its own hand-rolled `_row_matches` instead of the shared `SelectorFrequencyRule._matches` the other four rule types delegate to. So rather than fix the same bug a third time, `selector_frequency` gained `min_per_week`, both configs were migrated, and the type was **removed** — registration, class, `MenuRuleType` member and tests. `tests/rules/test_per_week_caps.py` asserts it is gone from `RULE_CLASSES` and that no config names it, because leaving it registered is what would let the next config reintroduce the defect. The general rule: if two rule types read the same config key, they have to agree on what it means, and the cheapest way to guarantee that is for only one of them to read it.

34. **The vegetarian line is the one ontology error with a consequence outside the software.** `PoolBuilder._nonveg_mask` reads `primary_protein` and `is_egg_dish` and decides two different things: a row it marks non-veg is dropped from every slot except `nonveg_main`/`nonveg_soup`, and a row it marks veg stays in the veg pools. So a **vegetarian dish marked non-veg** vanishes from the pool it belongs to and is offered as the day's meat dish, and a **meat dish marked vegetarian** is plated to someone who asked not to be served meat. Neither raises, neither logs, both plate. `vegnonveg_corrections.py` fixes 27 rows in both directions. **A name pattern is the wrong instrument here, and the two traps sit next to each other**: `keema` does NOT imply meat (soya, nutri/Nutrela and gobi keema are standard vegetarian North Indian dishes — minced soya or cauliflower standing in for mince), while `matar`/`mutter` does NOT imply vegetarian, because **Keema Matar IS the meat dish** — the peas are added to the mince, not substituted for it. A rule keyed on either word flips exactly the wrong row, so `soya_matar_keema` is corrected and `mutter_keema` is left alone. Same shape for `bhurji`, which means *scrambled* and not *egg*. **The enriched source bank cannot be appealed to**: it carries `primary_protein__source: original` and `__band: verified` on every one of these rows, where "verified" means the pass RETAINED the incoming value rather than that anyone checked it — and it files the family inconsistently, `soya_keema_mutter` as `soy`/`veg_dry` beside `soya_matar_keema` as `mutton`/`nonveg_main`, the same dish twice. That self-contradiction is the ontology's own evidence. **The other direction is a misspelling problem** and the same one `misspelled_protein_names.py` documented: `tandoori_chcien`, `chilli_chiken` and `kolkata_chic_curry` hid chicken dishes from every check that reads a name, including the vendor's own categorisation — the bank itself filed `tandoori_chcien` as `vegetable_north_indian_curry`/`paneer_curry`, so nothing downstream had a reason to doubt it, and `chilli_chiken` carried `is_chinese_veg_gravy`, making it eligible for a themed Chinese VEG gravy cell. **Three detection channels, and each found what the others could not.** A structural scan of the columns found the keemas and bhurjis; name-similarity against a known non-veg row found the four NCR misspellings and `kolkata_chic_curry`; and grouping dishes by a SYNONYM-normalised key (`audit_duplicate_dish_names.py`) found **`kori_gassi`** — Mangalorean CHICKEN curry, `kori` being Tulu for chicken, sitting in `veg_gravy` with no protein beside the correctly-filed `chicken_gassi`. Similarity scored those two names at ~0.5 and no English or Hindi meat-word list carries `kori`, so the first two channels were both blind to it. **Corrections are conservative in the direction that matters**: an arguable row is left NON-VEG and reported, because a vegetarian dish withheld is a worse menu and a meat dish served is a broken promise. Everything the client then resolved is recorded against its question in `docs/vegnonveg_to_confirm.csv` — `mutter_keema` is peas keema (veg), `kasturi_kebab` is chicken, `shami_kebab` and `gauloti_kebab` are non-veg, and the salad-bar rows and `hederabad_dum_biryani` were removed. Residual risk is measured: across all five cities exactly two non-veg rows carry no meat or egg word in any language these menus use, and both are correct.

33. **A verdict about solver behaviour must be tested against POOL AVAILABILITY, not rule adjacency.** Two independent analyses — `docs/explain_layer_calibration.md` and a later review — reached the same wrong conclusion about `no_ingredient_echo`, and the second looked more rigorous for having arithmetic attached to it. The method both used was: see a flag, find a rule that touches that slot, conclude the solver was forced. That reasoning is **unfalsifiable** — with 57 city rules and 175 client rules there is always a rule nearby — and it produced a confident 64% false-positive rate for something measured at 14%. The specific error: a `slot_composition` component constrains a CATEGORY (`is_nonveg_dry`), and inside that category the solver still chooses freely; attributing its free choice to the rule let it off the hook. Bangalore's `is_nonveg_dry` pool is 127 dishes of which 32 are not chicken, and `bread` is 335 of which 210 are not wheat — the solver had a way out both times and took the repeat anyway. **The question is always "could the solver have done otherwise?", and `pre_filter_pool()` always answers it.** This will recur: any future diagnostic — plate balance, cost per plate, nutrition targets — faces the same trap, where a heuristic flags something, someone finds a nearby rule, and a real finding gets suppressed. The two checks calibrated by the flawed method and NOT yet re-derived are recorded at the top of the calibration doc rather than quietly trusted.

32. **The theme tier is NOT lexicographic at `MAX_NUM_DAYS` — reproduced, and awaiting a decision.** `OBJECTIVE_TIER_WEIGHTS` is 1e15/1e12/1e9/1e6 and CP-SAT knows nothing about tiers — it maximises one integer sum — so "a higher-priority soft rule is never traded for a pile of lower ones" (rulebook §7) holds only while everything below a tier, added up, stays under one unit of it. That is a property of SIZE, not of the constants, and when it breaks the solve still returns OPTIMAL having optimised the wrong priority with nothing logged: the same silent shape as note 27. `tests/rules/test_objective_tier_headroom.py` builds the real model for the fleet's widest counter (Booking.com counter 0, 19 expanded slots) at `MAX_NUM_DAYS` and **finds a feasible assignment where the mass below THEME reaches 1.86e15 against a 1e15 tier weight (measured 2026-09-09; it was recorded as 1.02e15 when first reproduced, so the inversion is WIDER than first documented, not narrower)**. That is an achieved solution, not a loose bound, so the inversion is real; the test carries a strict `xfail` naming it. **Theme is structurally the rung to watch** — it has the whole ladder beneath it, while medium and high read comfortable only because they sit under fewer tiers. **Three bounds were tried and two were wrong**, which is why the guard asks CP-SAT rather than computing: summing coefficients treats competing variables as simultaneously satisfiable AND understates an IntVar term (`avoid_attribute_repeat` returns a recurrence counter that reaches its domain, not 1); multiplying each coefficient by its variable's range fixes that and then overstates badly, because those per-value maxima compete for the same days. The two gave 10× and 0.94× for the same model. `BestObjectiveBound()` is sound even on a timeout, and an ACHIEVED value at or above the weight is a proof — the guard reports "undecided" rather than passing when it has neither. **The fix is a wider separation and it is the client's call**: it changes every menu for every client. NB a uniform 1e4 step (the obvious suggestion) breaks the other end — freshness reaches 91,000 in a cell and must stay under one LOW unit, so LOW cannot drop to 1e4. **Separately, freshness across a plan** is one bonus per CELL capped at 90,000 across 516 cells = **47 LOW units**. Note 24's "any rule outranks freshness" is true **in a cell** — the scope it claims, and 11× clear there — and false across a plan, but only for a rule that binds 12+ cells (a weekly `selector_frequency` minimum, say), never for a single-cell preference. That is menu policy, so nothing was retuned; what is pinned is that even at full stretch the band cannot reach a MEDIUM rule (0.047 of a unit). The band is computed from the CONSTANTS, not the sampled coefficients, because a fixture with no saved history scores every freshness bonus at 0 and the whole file would pass while measuring nothing.

31. **A rule that degraded has to say so to a person, not to a log.** Sixteen sites in the rule layer under-enforce rather than fail — `selector_frequency` capping a `min` to what the pool can place, a daily or weekly floor relaxed for a thin day, a theme or weekday ban skipped because the slot had nothing else to offer, a `slot_composition` component dropped for want of a cell, `same_day_exclusion` standing down when both sides are forced, `attribute_grouping` giving up on alternation, `fixed_daily_item` going inert, and `unique_items` dropping uniqueness on a starved slot. Each is the right behaviour (note 9c) and each was a `logger.info`/`logger.warning` nobody reads, so a menu that quietly abandoned a rule looked exactly like one that satisfied it. `src/menu_rules/relaxations.py` is the channel: each site stamps `extra={RELAXATION: self.name}`, `/plan` wraps its solve in `RelaxationCapture` and returns the collected records (absent on a clean plan), the planner carries them into `/explain`, and `attach_relaxations` folds them into every EvidencePack so the rendered explanation names the rule that did not hold. **Four decisions, each against a silent failure.** (a) *A stamped field, not a log level* — 11 of the 16 are INFO and 3 of the tree's WARNINGs are not relaxations at all (a malformed rule config skipped at load time), so level does not separate the populations, and matching on message text breaks the first time a sentence is reworded; `tests/explain/test_relaxations.py` reads the AST and fails if a relaxation-shaped line is added without the stamp, with an allow-list for the three load-time ones. (b) *The level is lowered for the duration* — `logger.info` is dropped before any handler runs when the effective level is higher, so a deployment at WARNING would capture nothing and never say so; refcounted with the original level held once, because two overlapping captures each restoring "the level I saw" leaves the tree at INFO forever (the second saw the first's INFO) while restoring on the first exit makes the capture still running deaf. (c) *Thread-scoped* — `@solver_gate` runs two solves at once by design and every handler on a logger sees every record, so without the filter one client's explanation cites another client's relaxed rule; the same hazard as note 27, one layer up. (d) *Deduped on `record.msg`* — the format string, before interpolation, so a 25-day plan relaxing a daily floor yields one entry with `occurrences: 25` instead of 25 near-identical lines. `/explain` takes them as an INPUT rather than recomputing them because it never solves and they are observable only while the solver runs: drop them from the round trip and the explanation silently stops mentioning which rule bent.

29. **A day the client does not work is a BLANK column, not a missing one.** The horizon spans `num_days` **weekdays** (calendar days for a `serve_weekends` site), and the client then serves some subset: `_weekdays_from` counts up to `num_days` skipping Sat/Sun, then `_filter_dates_by_working_days` drops the weekdays a restricted-`working_days` client does not cook on (Clario Mon-Thu, Piramel Mon/Tue/Thu, Quince Wed/Thu/Fri — 3 of 61 clients). Those dropped dates used to be gone for good, so a 5-day horizon from Monday returned FOUR days for Clario: no Friday column at all, the gap closed up, and "5 days" quietly meant a different number of columns per client. Now `_prepare_solver_inputs` keeps both — `weekday_dates` is what the solver plans, `SolverInputs.span_dates` is what the menu is rendered over (`_span_dates` unions them, so a date the solver dropped is still shown). No solver change was needed: `SolutionFormatter` reads `week_plan.get(d, {})`, so a date with no plan formats as a day with no items, and no rule sees an extra day (`selector_frequency.apply` does `if not day_cells: continue`, so a blank Friday adds nothing to a `max_per_week` bucket). The blank day is **marked**, not just empty — `served_dates` gives it `is_working_day: False` and no theme, because a cuisine tag over an empty column reads as a day the solver FAILED on rather than one the kitchen is closed for; `ui.formatters.off_days_from_solution` reads the flag and `menu_table_html` renders a dimmed "Not served" header (`.day-off`). The Excel export needed nothing — it already builds cells with `plan.get(d, {}).get(slot_id, "")`. The planner's horizon **default** follows the client too (`_cached_week_length`): 7 for a weekend site, 5 otherwise, reset when the client changes because a keyed Streamlit widget would otherwise carry a 5 over to a weekend site. `tests/platform/test_non_working_days_are_blank.py`.

28. **`menu_history` is read back, so what `/save` writes has to be the ontology's own spelling.** The cooldown (`banned_items_by_date`), the freshness objective (`days_since_last_served`), the cross-week cadences (`selector_banned_by_date`) and the week signatures all compare the STORED STRING against the ontology's `item` column — `ItemCooldownMenuRule.pre_filter_pool` is literally `pool['item'].isin(banned)`. `/save` used to store whatever it was handed. A plan from this client's own `/plan` round-trips fine (`item_base` IS the ontology spelling), which is why nothing ever showed on the normal path; anything else failed **silently and in the worst direction** — a display name "Dal Tadka" stored as `dal tadka` matches no pool row, so the dish is never banned and never ages, with no log line, no diagnostic and a plausible menu every week. `api.app._canonicalise_saved_plan` now resolves each dish through the same space/underscore matching a `constant_items` pin uses (`_canonical_item_name`) and stores the ontology's spelling, turning the silent failure into a correct save rather than a warning about an incorrect one. It runs **before** the week signature, which is compared against future weeks and so must be computed over the stored spellings. What does not resolve is stored as given and returned in `unknown_items` (+ a `warning`; both keys absent on a clean save, so the body is unchanged when there is nothing to say) and logged — **never rejected**, for two reasons: an off-ontology pin is a real feature (note 9, five clients rely on it, so `_declared_constant_values` excludes them from the report), and a plan the user has just spent a solve generating must not be lost to a name we failed to recognise. A wrong cooldown is recoverable; a discarded plan is not. Same reasoning for the failure path: if the item list cannot be read at all, the save proceeds unvalidated. `tests/platform/test_save_canonicalises.py`.

27. **A rule instance may not be shared between two solves.** `OntologyRepository.rules_for_city` caches one ruleset per city for the process, and rules are not stateless: `UniqueItemsMenuRule.apply()` stores the model's repeat-penalty **variables** on `self` for `get_objective_terms()` to read back. `load_for_client` used to return that cached list unchanged for a client with no overrides — most of the fleet — so any two clients of one city solving concurrently (which `@solver_gate` allows by design: 1 active → 9 workers, 2 → 5 each) shared every rule object, and the second `apply()` clobbered the first's list. A CP-SAT expression carries variable INDICES, not objects, so the foreign variables are not detected as foreign; they are resolved against whichever model is solved. Measured (`tests/rules/test_rule_instance_isolation.py`): if the other model is **bigger** an index runs past this model's variable list and CP-SAT answers MODEL_INVALID → a 500; if it is the same size or **smaller** every index resolves to the WRONG variables, the solve returns OPTIMAL and the menu is served having optimised something unrelated, with nothing logged. The quiet case is the common one, so "it 500s under concurrency" understates it. Fixed in the loader (`MenuRuleLoader._rebuild`): `load_for_client` now always returns fresh instances, rebuilt from each rule's `config`. Costs one `_create_rule` per rule against a CP-SAT solve, and the override path always did it — the early return was the only sharing route. A rule that cannot be rebuilt is passed through rather than dropped, since losing a constraint silently is worse than the hazard. When adding per-solve state to a rule, this is the invariant that makes it safe. `UniqueItemsMenuRule._repeat_penalty_vars` is the sharp case but not the only writer: `diagnostics.run_diagnostics` assigns `rule._peer_rules = rules` on every rule that declares the hook (seven types do), and `SelectorFrequencyRule._forced_days` / `NonvegBiryaniWeeklyRule.forced_biryani_days` record `_forced_dates` for the per-week check in note 26 — all per-request writes onto what used to be a per-process object.

36. **Nothing in the solver looked at two dishes on ONE PLATE, and that is why menus read as repetitive.** `unique_items`, the item cooldown and the freshness objective all work ACROSS days; within a day the only cross-dish rules were colour variety and the hand-configured `same_day_exclusion` pairs. Key ingredient, protein, sub-category and texture were unconstrained on a plate, so a paneer gravy beside a paneer dry was legal under every rule in the system. `docs/explain_layer_calibration.md` measured the result over 49 real days: `no_ingredient_echo` fires on **29%** of them, and note 33 re-derived those repeats against POOL AVAILABILITY rather than rule adjacency — the solver had 32 non-chicken dry dishes and 210 non-wheat breads and repeated anyway. The detector was already calibrated; it had simply never been wired to the solver. **The fix is scoped, because the obvious version cannot be built.** A plate-wide "key ingredient must differ" is INFEASIBLE on day two for all 59 non-veg counters: `nonveg_main` carries **six** distinct key ingredients in the entire ontology and `nonveg_main_daily_pair` mandates a chicken gravy every day. The same holds wherever the ingredient IS the slot's identity — `dal`'s value is literally `dal` on all 59 counters that run it, `bread`'s is `wheat` on 64, `rice`'s is `mixed_vegetables` on 61. So the HARD rules are scoped to `veg_gravy` + `veg_dry` (`veg_plate_distinct_key_ingredient`, `veg_key_ingredient_three_day_gap`), measured beforehand as feasible on **all 78** counters running either slot, and everything else is a SOFT day-scoped penalty (`plate_key_ingredient_echo`) that chicken and wheat can outbid. **`key_ingredient` is blank on 36% of the Bangalore workbook** (38% Hyderabad, 33% Chennai, 23% Pune, 3% NCR) and a blank is *unconstrained* by `apply()`, so without `require_value` the rule is worse than useless — the solver escapes it by serving exactly the dishes nobody has classified. The drop stands down per slot where it would starve one: measured across the fleet only 9 counter-slots fall below the cooldown floor, but Booking.com's `nonveg_soup` and `infused_water` are 100% blank and would be emptied outright. NB the 36% was first measured as **0%** — `col.astype(str)` does not stringify NaN under pandas' `str` dtype, so `!= ''` reported an empty column as fully populated; `_has_value()` exists so no rule repeats that. The explain layer's own checks are the regression test for all of this, which is the point of having built the detector first.


37. **A blank column is not blank once `str()` has touched it, and that is how a variety rule becomes a penalty on the DATA'S GAPS.** The grouping sites in `attribute_grouping`, `soft_preference` and `selector_frequency` read a cell as `_norm_str(str(row.get(col, '')))`. `_norm_str` handles `pd.isna` — but `str()` runs first, so a float NaN arrives as the string `'nan'`, which is truthy, non-empty and IDENTICAL across every unclassified row. Harmless while the only `group_by` columns were ones `ColumnMapper` normalises (`key_ingredient`, `item_color`, `sub_category` all come through as `''`), and immediately wrong for the first one it does not: **`primary_protein` is NaN on 3,988 of Bangalore's 6,143 rows** and is not in that list, so "don't repeat a protein on the plate" would have read as "don't serve two dishes nobody has classified" — a penalty the solver satisfies by preferring classified dishes, which looks like the rule working. `_norm_cell` (`column_mapper.py`) is the one reader for a grouped column: `_norm_str` first, then `_BLANK_CELL_TEXT` (`nan`/`none`/`null`/`na`/`nat`/`-`) folded to `''`, so the literal text a workbook or a re-import can carry is caught as well as the float. `none` is in that set because the enriched workbooks wrote a literal "none" for "no protein focus" and `merge_enriched_ontology._norm` folds it on the way in — a hand edit can put it back. The same family as the `_has_value` artefact in note 36, one layer down and with the opposite symptom: there a blank column measured as fully populated, here a blank CELL measures as a shared value. An AST guard in `tests/data/test_protein_vocabulary.py` fails if `_norm_str(str(...))` returns to a column read, with a planted violation and a tolerated `str(r.get('item'))` so it cannot pass vacuously.

38. **The vegetarian plate now answers to its PROTEIN as well as its key ingredient, and the two rules make opposite calls about blanks.** Note 36's pair (`veg_plate_distinct_key_ingredient`, `plate_key_ingredient_echo`) left a gap the client named directly: a soya chaap gravy beside a soya keema dry, where the two rows carry different key ingredients and the same protein. Bangalore has 121 `primary_protein: soy` rows against 98 `key_ingredient: soy`, so 23 soya dishes were invisible to the first rule. Three rules close it — `veg_plate_distinct_protein` (HARD, `max_cells_per_day: 1` over veg_gravy + veg_dry, measured feasible on all 70 counters running 2+ veg cells), `plate_protein_echo` (soft/medium, `scope: day`, plate-wide) and `veg_week_protein_variety` (soft/medium, `scope: week`, the veg slots only). **`require_value` is OFF here, the opposite of the key_ingredient rule, and the difference is what the blank MEANS**: a blank `key_ingredient` is an unclassified dish and the solver escapes into it, while a blank `primary_protein` is the value the enriched workbooks wrote as literal `none` — two plain vegetable dishes are not a repeat, and dropping blanks would delete 56% of veg_gravy and 74% of veg_dry. The week rule is scoped to the veg slots rather than the plate because `nonveg_main` is 0% blank and serves chicken on nearly every day of nearly every week by mandate: plate-wide it would spend its whole budget on a repeat no counter can avoid. `plate_protein_echo` is MEDIUM rather than high for note 32's reason and not the client's — the theme tier is already measurably inverted at `MAX_NUM_DAYS`, a fifth high-tier soft rule widens that, and the firm half of the requirement is already a HARD constraint that outranks every soft tier. Related fix in `soft_preference._over`: the day scope's IntVar domain was `len(lits)`, the CANDIDATE count, when a cell takes exactly one candidate — so a value offered by 300 candidates across 6 cells declared a domain of 300. Loose for propagation, and `test_objective_tier_headroom` bounds a term by its variable's RANGE, so the slack counted as reachable mass against that same inverted tier.


40. **A regional day is a FLOOR, never a FILTER — and the measurement is what says so.** `state_origin` names the Indian state a dish comes from and is 100% FILLED and about 26% informative: all 2,724 Bangalore rows reading `Pan-North India` are `cuisine_family: north_indian` with `region_reason: no sub-regional signal`, so three rows in four are the ABSENCE of a region spelled as a value — the `fill_cuisine_family.py` situation again. The gate is **`admin_type ∈ {state, union_territory}`** and never `state_confidence` or `region_authority`: `high` is 9 rows in Bangalore, 1 in Chennai, **0 in Pune and Hyderabad**, and Pune/Hyderabad are 100% `NAME_LEXICON` with no `UNRESOLVED` bucket at all while Bangalore is 66% of it — the same pipeline did not run the same way per city, so a rule reading either column means something different in each. `is_single_state` is exactly `admin_type` (perfectly diagonal crosstab) and carries nothing extra. **Why a filter is impossible**: Bangalore holds 47 Punjabi veg gravies and **zero Punjabi rice and zero Punjabi bread**; Kerala has 4 rices, Telangana 2 veg dries, Maharashtra 0 breads. `ThemeSlotFilterRule`-style narrowing empties those slots, which is the deleted `ncr_south_bread` step's incident verbatim — three south breads, drained by the cooldown, INFEASIBLE with no starved slot to point at. So the floor's `base_slot` list is **derived from the region's own depth** (`Region.usable_slots`): Punjab's runs over gravy/dry/dal/non-veg/dessert and rice and bread are simply not in it, which keeps the floor always satisfiable AND keeps a `RELAXATION` meaning one thing — the pool ran out THIS WEEK — instead of also meaning "this city never had a Punjabi rice", which is a fact about the item list and belongs in the picker. Measured at a 4-distinct-dish floor (a weekly regional day recurs ~3× inside the 21-day cooldown, +1 for the week planned) only **one to three regions per city are themeable at all** — Bangalore/Hyderabad Tamil Nadu/Karnataka/Andhra, Chennai Tamil Nadu ONLY, NCR and Pune a partial day — so the picker offers what the city can serve and greys the rest out *with their counts*, because a region silently missing reads as forgotten rather than weighed. **Every region nests inside ONE `cuisine_family`** (TN/Karnataka/Kerala/Andhra/Telangana 100% south, Punjab/Maharashtra/Bengal/Rajasthan/UP/Gujarat/J&K 100% north), so the theme↔region compatibility matrix is DERIVED from the workbook and cannot drift — and that nesting is also why the layer is worth having, since `cuisine_family` files Maharashtra, Punjab and Bengal alike and structurally cannot tell a Maharashtrian Friday from a Punjabi one. **No new rule type**: two selector keys (`state_origin`, `admin_type`), one scope key (`only_on_dates`) and one soft mode (`prefer_cells`). `only_on_dates` SCOPES and does not BAN — `allowed_day_types` forbids the selector on days it does not list, and getting that backwards would turn "serve three Tamil dishes on Thursday" into "serve no Tamil food Monday to Wednesday"; an unparseable date makes the rule inert rather than universal, the safe direction for a scope key. **It lives on the PLANNER behind an OFF-by-default sidebar toggle**, not in Edit Logic: picking a region is a weekly editorial decision and has to work AFTER a plan exists, so Apply re-solves ONE day through `/regenerate`, which locks every other cell — the week's no-repeat rule, the cooldown, the freshness objective and the cross-counter sync all still hold. `clients.region_map` is the optional second step ("save as weekly default"), validated at the PUT against the city's own regions rather than dropped at solve time (note 9's silent mismatch). **Today the whole feature is inert**: no committed workbook carries the columns, `/api/v1/regions` answers `available: false`, and `test_regional_days.py` pins that — when the corrected workbooks are installed, that failing test is what says the feature just switched on.

39. **A day's services are separate SOLVES, so nothing inside the solver can keep them apart.** `clients.meals` is an ordered LIST — `breakfast`/`lunch`/`snacks`/`dinner`, defaulting to lunch+dinner for every client — and each entry gets its own menu per Generate click. It began as a `serve_dinner` boolean, which could only express "lunch, and maybe dinner"; the list is why `MEALS` is ordered by when a service is EATEN rather than how anyone lists it, since that tuple is the solve order and each service is handed every EARLIER one's dishes to avoid (accumulated by `_merge_exclusions` — passing only the previous service is the easy mistake and it fails quietly, the menu still rendering while dinner reprints breakfast). Every mechanism that stops a dish repeating is scoped to one model or to saved history: `unique_items` lives inside a single CP-SAT model, the item cooldown and the cross-week cadences read `menu_history`, and neither sees a sibling solve running in the same second. So the separation is done by the CALLER — the planner solves lunch, hands its dishes to dinner as `/plan`'s `exclude_items`, and the server folds them into `banned_by_date`, which is the map every rule and the whole pre-flight already respect (`_merge_excluded_items`). **Every lunch dish is banned on every DAY of the horizon**, not only its own, because the failure this prevents is Monday's lunch dal turning up at Wednesday's dinner INSIDE one generation, which no cooldown can catch — the cooldown fires on the next plan, after the duplicate is printed. Staples are deliberately not filtered out of the exclusion: they do not need to be, since the item-cooldown pre-filter exempts a declared staple from that same map, so the daily curd and the plain chapati still repeat at dinner, which is what a canteen serves. **Keyed per COUNTER, not pooled across the site**: pooling a six-counter client's lunch would ban eighty dishes from every dinner cell and starve the thin pools, to prevent a collision between two stations no diner stands in front of. `menu_history`'s PK widens to `(client_name, service_date, meal)`, and **`/save` writes BOTH services** — an unsaved dinner is not a gap the next plan notices, it is a menu the cooldown and the freshness objective never heard of, so the following week reprints it. `load_saved_plan` matches the meal in PYTHON rather than with a server-side `.eq`, so a database that has not run the migration degrades to "everything is lunch" instead of returning nothing. The 35-40% difference the client asked for is **measured and reported, never constrained** (`ui.formatters.meal_difference`, `MIN_MEAL_DIFFERENCE`): the exclusion overshoots that floor by a wide margin so a CP-SAT bound would be machinery for a condition that never binds, but a guarantee nothing measures is one that quietly stops holding — the planner captions the number and names the days if any fall below. UI shape: `st.session_state.meal_blocks` holds one block list per service and `plan_blocks` MIRRORS the selected one (the same list object, so a regenerate on the dinner tab mutates the stored dinner), which leaves the table, the regenerate expander, the explanation and the Excel export as one code path that has no idea two meals exist; a one-meal client never sees the switcher. Both generation branches were folded into one `_solve_counters` pass for the same reason — two code paths for one operation drift, and only one of them gets the next fix. **The cross-service no-repeat is EMERGENT, and that is the hazard.** "A dish served at lunch does not come back at dinner for three weeks, or the other way round" is a real guarantee that nothing is named after: it falls out of `_build_history_context` querying `menu_history` by client and date range with **no meal filter**, `explode_history_rows` DROPPING the `meal` column when it flattens rows into the `(client, date, slot, item)` shape the cooldown reads, and `/save` writing both services. Add `.eq('meal', meal)` to the first as an obvious optimisation and the whole requirement vanishes with nothing failing and no log line — lunch simply stops seeing dinner and the menus still look fine. `tests/clients/test_cross_service_no_repeat.py` holds it down, including a lexical check on the query itself, because the filter's ABSENCE is the feature and absence has no runtime signal. The window is `DEFAULT_ITEM_COOLDOWN_DAYS` = **21**, which moved to `src/constants.py` because three places carried their own copy of it (the rule default, `banned_items_by_date`, and `clients.item_cooldown_days`'s default) and three copies of a window are three things that can disagree. NB the column overrides the default and 62 of 66 client rows store an explicit 20, so raising the default alone moves nobody — that is owner data, not config.

41. **The rest of a themed plate was never themed at all, and the column that says which dish is which is `sub_category`, not the flags.** `EXEMPT_FROM_CUISINE` is canonical and a config can only ADD to it, so `soup`, `salad` and `starter` are never narrowed by the theme filter — correct for an infused water, wrong for a Chinese day, which served an Indian soup and an Indian salad with nothing saying so. `_CHINESE_FLAG_MAP` covers only `rice`, `veg_gravy` and `nonveg_main`, so bread came back whatever the pool offered. **`slot_pool_by_theme`** (`{theme: {slot: selector}}`, parsed by `SelectorFrequencyRule._parse_matcher` so there is one selector dialect rather than two that drift) is the one thing that beats the exemption, because it is written down rather than inferred; it runs ahead of the theme dispatch and **returns**, since falling through would hand a Chinese day's bread to `_filter_chinese` and no city's list holds a Chinese bread. It **degrades on the slot's CELL COUNT, not on emptiness**: NCR holds exactly one Chinese salad and a two-salad counter narrowed to it is INFEASIBLE on uniqueness while one that kept the ordinary pool plans fine — one dish is worse than none, `_combo_variant_cells`'s lesson in a second place — and the shortfall is stamped (note 31), which is what Chennai's zero Chinese salads produce on every Chinese day. **The companion rule is `south_bread_south_day_only`**, and it is where the flag-vs-column question was settled by measurement: `is_dosa_family` + `is_rice_bread` catch 75 of Bangalore's 321 breads while the eight dosa/idly/uthappam/adai/`rotis` sub_categories catch 86 (union 88), and in Chennai 42 against 61 — the 20 Chennai rows the flags miss include `idli` itself, `masala_idli`, `podi_idli`, `onion_uthappam` and `pesarattu`. Written against the flags alone the rule moved the dosas off a biryani Monday and a mix Wednesday and left `masala_idli` and `tri_color_idli` standing in their place, which a generated week found and the configuration could not. Both flags are kept as extra `any_of` branches for the 3 rows filed the other way (`jeera_chapati_dosa`, `methi_chapati_dosa`, `mexican_dosa`). **Not matched on the dish NAME**: `appam_chapati` is a plain chapati, `dosakai_sambar` is a cucumber sambar, and `akki` is inside `sabakki` and `avalakki`. **A sub_category means different things in different cities**, which is why there is no shared branch list and no rule at all in Pune: `rotis` is akki/ragi/jowar roti in Bangalore and Hyderabad and bajara/jowar/rice BHAKARI in Pune, and Pune's list holds no dosa, no idly and no uthappam, so two of the three branches would match nothing and the third would hold Maharashtrian bread back for a South Indian day. `tests/rules/test_theme_slot_pools.py` walks every branch against its OWN city's list and fails on one that matches no bread — note 9, one branch at a time — and solves a real Bangalore and a real Chennai week, because all of the above was invisible in the config. **Known gap, deliberate**: the narrowing is not mirrored in `_project_filter_size`, because `diagnose()` skips every slot in `exempt_slots` — exactly the set this overrides — and `_project_filter_size` cannot see `slot_counts`, so it could not tell a narrowing from a stand-down. The stand-down already reaches /plan by name through the relaxation channel; the pre-flight would only say it sooner. Marked `ponytail:` at the site with the upgrade path.
